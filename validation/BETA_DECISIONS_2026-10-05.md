# BETA 설계 결정 갱신 — 2026-10-05 (shadow.5 자료 반영)

[설계 결정](ASSIST_BETA_DESIGN_2026-10-05.md)과 [주행 분석](TRIP_SHADOW5_2026-10-05.md), 독립 검토 두 건(OEM 경로·잘못된 위치 경로), 설계 영향 분석 두 건(Opus·Fable)을 합쳐 확정한다. 이 기록은 차량 시험이나 ASSIST 활성화를 승인하지 않는다.

## 1. 위치 상태 분류(송신 시점에 관측 가능한 것)

- **NO_FIX**: mode 1/2이고 utc_s=0(부팅 후 fix 없음, 저장값). 두 주행에서 12~15분 지속, 저장값은 부팅 사이에 바이트 단위로 같고 나이를 알 수 없다.
- **FIX**: mode 1/2이고 utc_s>0이 이전보다 증가.
- **LOST**: mode 0(fix 뒤 단절, 10-04 끝에서 관측; utc는 계속 증가, 좌표·방위·속도 동결, HDOP 99/99).
- 그 밖: mode 3, 해독 불가, utc 정체(>3초 증가 없음)는 원본 통과. 분류 키는 mode와 GetPosition의 utc_s이며 HDOP는 키가 아니다.

## 2. 처리

- **NO_FIX 구간(S1)**: 저장 위치·방위는 앵커가 될 수 없고(나이 미상, 방위 약 100° 어긋남 관측, 위치 44~195 m 어긋남) 위치·방위 치환은 금지한다. **속도만 덮어쓰기(Fable안)**: 복사본에서 바이트 32~39(`hasSpeed=1`, 속도)만 휠 속도로 바꾸고 나머지 40바이트는 원본이며 정확도 주장을 추가하지 않는다. 정지(네 바퀴 0)이면 0.
  출하 조건: 정지 좌표+정확도 8.8 m+속도 변동을 10분 이상 보낸 DHU 시험에서 네이버가 끊김 없이 속도를 표시해야 한다. 끊김이 되면 정확도 필드를 지워 "GPS 끊김" 형식으로 내리는 안(Opus안)으로 바꾼다.
  G2(방위)는 이 구간에서 달성할 수 없으며 그렇게 문서화한다.
- **LOST 구간(S3)**: 원래 설계의 DR 치환(정직한 예산 40 m, 앵커 게이트). 예산을 넘으면 원본.
- **FIX 구간**: 원본(NOT_UNKNOWN) 유지.

## 3. 앵커 게이트와 예산 수정(독립 검토 지적 반영)

1. 앵커 쌍은 utc가 이전보다 **엄격히 증가**하고(차이 ≤2초) 같은 utc는 비교 기준을 갱신하지 않는다. UTC 경과와 수신 mono 경과가 일치해야 한다.
2. HDOP ≤ 3.0 필수. 쌍 변위가 속도×dt의 [0.5, 1.5]배. 첫 fix 직후 연속 증가 fix가 10초 쌓이기 전에는 앵커 금지. GPS 복귀 직후도 같은 대기. 모든 거부 사유를 journal에 남긴다.
3. 위치 정확도에 **회전 항**을 넣는다: 위치 예산의 방위 성분을 hb(τ) = 0.03 + 0.002·τ + 0.10·누적|회전|으로 하고 ∫v·hb dτ를 쓴다(방위 20° 철회 판단은 유지).
4. 후진 래치: 래치=후진인데 휠 속도 15 km/h 초과가 2초 넘게 이어지면 철회(BETA는 앵커를 다시 받을 때까지 정지). 후진 1→0 전이를 한 번도 보지 못했으면 켜지 않는다. 래치는 모든 리셋과 REVERSE 제외 때 지운다.
5. yaw 영점은 **고정 2048**(두 주행의 정지·주행 추정 2045~2050의 중간), 정지 영점 자동 보정 금지(시동 직후 정지 영점 2037.7은 주행 최적값에서 12카운트 어긋났다). 방위 예산의 k=0.002는 ±3카운트를 덮는다.
6. 어댑터: `hold`를 세울 때 어댑터가 `invalidate()`도 한다(`allow_beta`이면 `beta_event` 필수). `DrSnapshot`의 기본값 초기화(NSDMI)를 없애고 `static_assert`로 trivial 생성을 보장한다. `choose_beta`는 UNOBSERVED를 "설치가 명시적으로 거절한 경우"에만 받는다.
7. **설치 결함**: BETA에서 세션 판독기를 바꾸면 설치기가 거부한다(실제 BLM+libpatch 0.10.0 QEMU 재현). 판독기는 항상 순정으로 두고 송신 쪽 저장소 관찰은 별도 후크(`Options.send_storage`)로 분리한다. 차량 libpatch는 0.9.1이므로 0.9.1로도 설치를 검증한다.
8. 판정 블록 버그와 로그 속도(문서 보정)는 별도로 수정한다([주행 분석](TRIP_SHADOW5_2026-10-05.md)).

## 4. 출하 전 검증

T6 재생(10-05의 191~714초 523건 전부 속도 덮어쓰기, DR 치환 0건, 727초 FIX에서 ARMED 복귀; 10-04는 mode 1에서 치환 0건, 1453초 LOST 전이와 예산 내 철회), DHU wire 시험(위 출하 조건), 결함 주입, 실제 BLM+libpatch(0.9.1과 0.10.0) QEMU, 독립 재검토.

## 5. F1/F2 반영 결과 (2026-10-05 추가 기록)

위 1~4절은 결정 당시 기록이며 고치지 않는다. 이 절은 그 뒤 구현(F1: `e03ba71`, `eb51810`, `c494dd8`, `f23b66d`, `b06053e`; F2: `8c81d13`, `2f5c591`, `4ca63e8`, `b2efb2b`, `3b53d8f`)에서 정한 해석과 정직한 한계를 덧붙인다. 모두 호스트·재생 시험 결과이며 차량, DHU, 폰 증거가 아니다. 이 기록도 차량 시험이나 ASSIST 활성화를 승인하지 않는다.

### 5.1 NO_FIX 속도 덮어쓰기와 위치 상태 의미

- 송신 시점 분류는 1절 그대로다(NO_FIX = mode 1/2이고 utc 0). NO_FIX 송신에는 choice 4(`BETA_SPEED_OVERLAY`)만 허용하고 바이트 32(`hasSpeed=1`)와 36~39(속도)만 바꾼다. 원본 좌표가 이 POSITION의 좌표와 1e-7도 한 단위 안에서 같지 않으면 `OVERLAY_MISMATCH`(15), 원본에 속도가 없고 바퀴가 서 있으면 `OVERLAY_NOT_NEEDED`(16)로 원본을 보낸다.
- DR 위치 치환(choice 3)은 class LOST만 받는다. F2에서 어댑터 `choose_beta`도 `position_class==LOST`를 직접 요구한다(현재 분류는 해독된 mode 0을 모두 LOST로 두므로 방어용).
- WITHDRAWN은 FIX(`gps_returned`)나 NATIVE_DR(`native_dr`)에서만 끝난다. UNDECODED(동시 분류 포함), UTC_STALL, LOST, NO_FIX 한 번으로는 풀리지 않는다. 이전에는 다른 class 한 번(예: mode 5)이 같은 단절 안에서 ARMED→GPS_LOST 재진입을 허용했다(`test_worker_beta withdrawn_class`로 재현·수정).
- NO_FIX 철회는 구간 전체가 아니다. 송신 실패 hold는 어댑터가 hold를 푼 뒤(원본 LOCATION 송신 결과 0) 2초, 세션 저장소 변화(폰·동글 재연결)는 마지막 변화 뒤 5초가 지나면 `WITHDRAWN>ARMED`(`rearm_after_hold`/`rearm_after_storage`)로 다시 무장한다. LOST 철회는 설계 3.8대로 그 단절 전체를 유지한다.
- 오프라인 판정(`analyze_logs.py`)은 정상 NO_FIX 덮어쓰기를 위반으로 보지 않고, 다른 class의 덮어쓰기, 허용 밖 바이트 변경, 송신 전 0.5초 안 바퀴 속도와 1 mm/s 넘게 다른 속도를 위반으로 본다.

### 5.2 후진 래치 해석

- 3.4의 "후진 1→0 전이를 본 적이 있어야 한다"는 F1에서 **같은 producer의 첫 메시지가 전진(0)이어도 관측으로 센다**로 해석했다. 근거: shadow.5 주행에서 reverse=1이 4회(528.8, 542.9, 588.7, 699.8초) 기록됐고 커널의 후방카메라 켜짐과 0.4초 안에서 일치했다. 따라서 "producer가 항상 0만 보낸다"는 가설은 이 자료로 반박되며, 0은 실제 전진 상태를 나타낸다고 본다(차량 한 대·한 주행의 관측이며 사양 확인은 아니다).
- 래치는 같은 producer의 짧은 입력 공백(누락 16건 이하, 2초 이하, 거부된 이벤트가 REVERSE가 아님)을 넘어 유지하고, 그보다 긴 공백·거부·리셋에서는 지운다. 유지와 해제는 `beta_reverse_latch`(MODEL 영역) 행으로 남는다.

### 5.3 예산의 기준점과 G2(지하주차장)의 실제 범위

- 60초·40 m·20° 예산은 **GPS를 잃은 시점이 아니라 마지막으로 받아들인 앵커(`beta_anchor` gate `ACCEPTED`)부터** 흐른다. 앵커는 3.2의 조건(HDOP ≤3, 속도 20~60 km/h, 연속 fix 10초 등)을 만족한 fix에서만 갱신된다.
- `beta_profile()` 값(앵커 20 m, 방위 0.03 rad, 0.002 rad/s, 속도 0.3 m/s, 임대 0.5 s)으로 계산하면 직선 주행에서 보고 정확도가 40 m에 닿는 시간은 30 km/h에서 약 21초, 50 km/h에서 약 14초이고, 90° 회전이 있으면 약 16초로 줄어든다.
- 실제 mode 0 기록은 2026-10-04 주차장 진입 한 번뿐이다. 재생(`replay_beta --real-only`, 비공개 자료)에서 마지막 ACCEPTED 앵커는 단절 약 25초 전(1429.2초, 21 km/h)이었고 그 뒤 20 km/h 미만 진입과 90° 회전이 이어져, GPS_LOST(1454.6초) 시점에 이미 `budget_limit`였다. BETA 치환은 0건이다.
- 따라서 지하주차장의 LOST DR(G2)은 현재 규칙으로 **사실상 달성되지 않는다**. 앵커가 단절 직전까지 갱신되는, 속도를 유지한 터널 진입에서만 10~15초 정도의 치환 창이 예상된다(재생 추정). 예산을 늘려 이를 바꾸는 것은 정확도 규칙을 다시 정하는 별도 결정이다.

### 5.4 DHU·차량만 답할 수 있는 남은 질문

1. 정지 좌표와 정확도 8.8 m에 움직이는 속도를 오래(10분 이상) 보낼 때 네이버의 동작(2절 출하 조건).
2. 저장 방위(예: 335°)가 그대로인 채 속도만 움직일 때 화살표가 이상하게 움직이는지. 그렇다면 덮어쓰기에서 바이트 40(`hasBearing`)도 지우는 안을 검토한다.
3. 실제 fix의 HDOP: AA LOCATION 행에는 정확도만 있고 앵커 게이트의 HDOP는 GetPosition 값이다. 실제 fix 구간의 AA 행 HDOP 대응은 아직 보지 못했다.
4. 300 ms를 넘는 센서 공백(shadow.5에서 1.6~2.1초 공백 관측)의 원인과 빈도.
5. 차량의 libpatch 0.9.1과 함께 설치된 후킹에서 터치·HUD·km/L 정상 여부(로그로 확인 불가).
6. 실외 주행 중에도 12분 동안 fix가 없었던 원인.
