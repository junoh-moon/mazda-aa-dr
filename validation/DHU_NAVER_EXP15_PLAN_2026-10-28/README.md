# DHU 시험 15 설계: 폰 위치에 갇힌 조건에서 v1.0 터널 교체(25 m 상한)의 화면 효과 — 2026-10-28

**상태: 설계만 있습니다.** 명령 생성기, 폰 모의 위치 구동기, 시험, 에이전트 지시문은 **아직 구현하지 않았습니다**(9절). 실행하려면 소유자 결정 두 가지가 먼저 필요합니다(7절). 아래 판정 표는 실행 전에 고정하는 사전 등록이며, 관찰 기록이 아닙니다.

## 1. 질문

v1.0.0에서 기본으로 켜진 터널 교체는 GPS 상실 동안 DR 위치·속도·방위를 보내고, 정확도를 `min(정직 예산, 25 m)`로 보고합니다. 이 25 m 상한은 실차 회색·고정의 기제로 추정한 "폰 위치에 갇힘"을 풀기 위해 넣었습니다. 그런데 **그 조건에서 실제로 풀리는지는 한 번도 관찰된 적이 없습니다.** 실제 터널 0건, DHU 0건입니다.

> Q. 네이버가 터널 입구에서 폰 자체 위치로 전환된 상태에서, 차 쪽 위치를 25 m로 보고하면 다시 차로 돌아와 회색 없이 속도를 따라가는가? 40 m와 순정에서는 갇히는가?

## 2. 이전 DHU가 답하지 못한 이유

| 내용 | 분류 | 출처 |
|---|---|---|
| 네이버는 안드로이드 오토에서 차 위치(`"car"`)와 폰 자체 위치(Fused·`"gps"`)를 **둘 다** 받고, 이중 선택기가 고른다. 전환에 연속 3회가 필요하고, 둘 다 무효이면 현재 소스를 유지한다 | DATA(정적 분석) | NAVER_MAP_APP_STATIC_RE_2026-10-12 |
| 유효 조건: 정확도 < 30 m, 수신 시각 새것, 경로 거리 < 1.5×도로폭. 연속 10틱 무효 → INVALID(터널 링크면 회색 TUNNEL 아이콘) | DATA | 같은 기록 |
| 갇힘 기제: 입구의 순정 mode-0은 정확도가 없어 차가 무효 → 폰이 유효하면 폰으로 전환 → 폰 GPS가 죽으면 둘 다 무효라 폰 유지 → 회색·가상주행으로 속도 고정 → 40 m인 차는 다시 유효가 되지 못함 | INFERENCE | 같은 기록 §22 |
| 실차 40 m 시절 터널 4건 중 회색·고정 3건 | DATA | G1_FIRST_TUNNELS_2026-10-11, LOG_AUDIT_TUNNELS_2026-10-12 |
| **벤치 폰은 경로 위에서 유효한 적이 없다**(집 위치, 경로 밖). 그래서 DHU는 갇힘 조건을 만들지 못했다. 시험 12 대조군(30→40 m)도 회색을 재현하지 못했다 | FACT | DHU_NAVER_EXP12_RESULT_2026-10-12 |
| 모의 위치에는 이름표만 붙고 감점·거부가 없다(6.8, 6.11 모두) | DATA | NAVER_MAP_APP_STATIC_RE, NAVER_MAP_6_11_DIFF_2026-10-13 |
| `navi.config`의 `trace=1`로 네이버가 자기 판단(차↔폰 전환, 무효, 회색, 가상주행)을 파일에 남긴다. 도우미 스크립트가 있다 | FACT | NAVER_MAP_LOGGING_2026-10-13, NAVER_TRACE_HELPER_2026-10-13 |

**새로 조작하는 변수는 폰 자체 위치입니다.** 지금까지의 DHU는 사실상 "폰 무효" 조건만 시험했습니다.

## 3. 조작

- **P1(갇힘 조건):** adb의 위치 test provider로 폰 `gps`·`network`에 **경로 위의 같은 위치**를 1 Hz로 넣습니다(정확도 5 m, 속도·방위 포함, 차 스트림과 같은 시계). 터널 입구 시각에 갱신을 멈춥니다. 실제 터널에서 폰 GPS가 끊기는 것과 같은 모양입니다.
- **P0(폰 무효, 이전 DHU와 같음):** test provider 없이 그대로 둡니다.
- **차 스트림 C(DHU `location` 명령):**
  - `STOCK`: 입구부터 순정 mode-0 모양(마지막 좌표 반복, 정확도 없음). 줄 형식은 구현 때 실차 `send` 기록의 mode-0 바이트에서 정하며, 추측으로 채우지 않습니다.
  - `CAP40`: 아래 터널 위치를 정확도 40 m로 보냅니다(메뉴 10을 끈 이전 상한).
  - `CAP25`: 같은 위치를 정확도 25 m로 보냅니다(**v1.0 기본**).
- C의 세 줄기는 정확도 낱말(또는 STOCK의 mode-0 모양)만 다릅니다. 위치·속도·방위·사진 시각은 같습니다.

### 경로와 시간표(공통)

시험 13의 서울 신월여의지하도로 동쪽 방향 경로(ODbL, 시험 13 `geometry/` 재사용)를 씁니다. 분기에 닿기 전에 끝나게 잘라 분기 변수를 없앱니다.

| 구간 | t | 차 스트림 | 폰(P1) |
|---|---|---|---|
| 접근 | 0–19 s | 정확도 1 m, 20 m/s, 경로 위 | 같은 위치 5 m |
| 터널 A | 20–44 s | C, 20 m/s | **갱신 멈춤** |
| 터널 B | 45–69 s | C, **11 m/s**(속도 변화 = G1의 관찰 대상) | 멈춤 |
| 터널 C | 70–89 s | C, 20 m/s | 멈춤 |
| 출구 | 90–104 s | 정확도 1 m(GPS 복귀) | 갱신 재개 |

위치는 경로 중심선 위에 둡니다(옆 오차 0). 이 시험은 **정확도 상한만의 효과**를 봅니다. 옆 오차가 도로폭 기준을 넘는 긴 터널(60 s 사례의 off-route 회색)은 범위 밖입니다.

## 4. 회차와 순서

회차는 `P1-STOCK`, `P1-CAP40`, `P1-CAP25`, `P0-CAP25`이며, 각 2회입니다.

회기 사이 변동(시험 12의 교훈)을 줄이려고 ABBA 순서를 씁니다. `P1-STOCK → P1-CAP40 → P1-CAP25 → P0-CAP25 → P0-CAP25 → P1-CAP25 → P1-CAP40 → P1-STOCK`입니다. 회차 사이에는 안내 종료 → 폰 provider 위치를 출발점으로 재설정 → 경로 재설정을 합니다. 회차당 약 2.5분, 회기 약 30분입니다.

## 5. 판독

1. **네이버 trace(주 판독, 객관):** 전환 줄("Switching to …", "Prefer invalid…", "Mobile resumed…"), `LocationStatus` INVALID 진입·해제, 가상주행·정지 줄. 회차마다 입구 기준 시각으로 정렬합니다.
2. **사진(보조):** 5 s마다 회색 아이콘 유무, 화면 속도(km/h), 화살표 진행, 재탐색 문구.
3. **스트림 기록:** 보낸 값과 폰 provider에 넣은 값(시각 포함)을 회차마다 남깁니다.

판독 이름(사전 고정):

- `SRC-CAR` / `SRC-PHONE`: 입구 +s 시점의 선택 소스. trace 전환 줄로 판정합니다.
- `GREY`: INVALID 진입 또는 회색 아이콘. 그 시각을 기록합니다.
- `SPD-FOLLOW`: 구간 B·C에서 보낸 속도의 ±5 km/h가 구간 시작 3 s 안에 표시되고 유지됨.
- `SPD-FROZEN`: 구간이 바뀌어도 화면 속도가 그대로임.
- `EXIT-OK`: 출구 뒤 5 s 안에 정상 아이콘과 출구 위치.

## 6. 사전 등록 판정

**관문 M(조작 확인, Tier 0):** 차 스트림을 정확도 없음으로 두고 P1 위치만 넣었을 때, trace에 폰 전환이 남고 화면 위치가 폰 값을 따라야 합니다. 실패하면 **ABORT**합니다. 조작이 안 됐으므로 제품 결론은 없습니다.

**관문 T(갇힘 재현):** `P1-STOCK` 2회 모두 `SRC-PHONE` 그리고 입구 +15 s 안에 `GREY`여야 합니다. 1회 이하이면 **INCONCLUSIVE**(시험 12의 P-2와 같은 처리)이고, 아래 H 판정을 하지 않습니다.

관문 T를 통과했을 때:

| 판정 | 조건(2회 모두) | 의미 |
|---|---|---|
| **H-25OK** | `P1-CAP25`: 입구 +5 s 안에 `SRC-CAR`로 돌아오거나 계속 `SRC-CAR`, `GREY` 없음, 구간 B·C `SPD-FOLLOW`, `EXIT-OK`. 그리고 `P1-CAP40`은 1회 이상 갇힘(`SRC-PHONE`+`GREY`) | 25 m 상한이 갇힘을 푼다. v1.0 기본 터널 교체의 화면 효과가 **오프라인 검증(DHU)**으로 올라간다(실차 미검증 유지) |
| **H-BOTH-OK** | CAP25·CAP40 모두 갇히지 않음 | 차 위치가 있으면 40 m도 갇히지 않음. 갇힘 기제(§22)가 설치 버전에서 다르다는 뜻이며 25 m의 근거가 약해진다. 실차 회색 원인은 다른 곳(옆 오차 등)으로 재조사 |
| **H-25FAIL** | `P1-CAP25`도 갇힘 | 25 m 상한은 이 기제를 풀지 못한다. 기본 켜짐 터널 교체의 화면 이득이 순정 대비 없음. 기본값 재검토 근거(제품 변경은 별도 결정) |
| **H-HARM** | `P1-CAP25`가 `P1-STOCK`보다 나쁨(재탐색, 출구에서 순정에 없던 점프·이탈) | 기본 켜짐 기능의 해 가능성. 메뉴 10/기본값 재검토를 우선 보고 |
| **H-MIXED** | 2회가 다름 | 약한 증거. 추가 반복 전에는 결론 없음 |

`P0-CAP25`는 시험 12의 25 m 정상 결과(폰 무효 조건)를 재현하는지 보는 보조 대조이며, 판정을 바꾸지 않습니다.

## 7. 소유자 결정이 필요한 것

이전 DHU의 "폰 설정을 바꾸지 않는다" 원칙을 이번에는 지킬 수 없습니다. 두 가지 모두 되돌릴 수 있지만 명시 승인이 필요합니다.

1. **폰 위치 test provider:** `appops set com.android.shell android:mock_location allow`, `cmd location providers add-test-provider gps|network`, 끝나면 `remove-test-provider`와 appops 원복. 실행 중 폰의 다른 앱도 모의 위치를 받습니다. 에이전트가 비정상 종료하면 남을 수 있으므로 원복 스크립트와 소유자용 한 줄 원복 명령을 함께 둡니다. Samsung S25(Android 15/16)에서 shell이 test provider를 만들 수 있는지는 **확인되지 않았습니다**. 관문 M 전에 읽기 전용 점검과 1회 생성·삭제로 확인합니다.
2. **네이버 `navi.config` `trace=1`:** 기존 도우미 `enable.sh`/`disable.sh`를 씁니다. trace에는 정밀 좌표가 들어가지만, 이번에는 합성 경로뿐이라 개인 위치는 담기지 않습니다. 다만 test provider가 없는 회차·시간에는 폰 실제 위치가 들어갈 수 있으므로, trace는 비공개 보관하고 공유하지 않습니다.

## 8. 한계

- DHU는 Mazda 와이어, 제품 코드, 실차 GPS 상태 판정을 실행하지 않습니다. 이 시험은 **설치된 네이버가 이 입력 모양에 어떻게 반응하는가**만 봅니다.
- 폰 GPS의 실제 상실 모양(정확도가 점점 나빠짐, network 위치의 잔존)을 "갱신 멈춤"으로 단순화했습니다. 이 단순화로 갇힘이 더 쉽게 또는 더 어렵게 생길 수 있습니다.
- Fused provider(Play 서비스 내부, 분석 범위 밖)가 test provider 값을 어떻게 섞는지는 모릅니다. 관문 M이 실제 동작을 확인합니다.
- 옆 오차 0, 분기 없음, 짧은 터널(70 s)입니다. 긴 터널의 off-route 회색, 출구 점프(실측 120.6 m)는 범위 밖입니다.
- 네이버·안드로이드 오토 버전에 종속됩니다. 실행 때 버전을 기록하며, 분석 버전(6.8/6.11)과 다르면 그 사실을 적습니다.
- 회차당 2회입니다. 결과는 약한 증거이며 G1 해결을 주장하지 않습니다.

## 9. 아직 구현하지 않은 것

- `gen_commands.py`: 시험 13 geometry에서 위 시간표의 DHU 명령 파일(4 줄기 × 회차)과 `run-plan.json`(사진 시각, 보낸 값, 폰 provider 값)을 만드는 생성기, 그리고 그 시험.
- 폰 모의 위치 구동기: DHU 명령 전송과 같은 시계로 `cmd location providers set-test-provider-location`을 1 Hz로 보내고 입구에서 멈추는 스크립트. 시작 전 점검, 종료·중단 시 원복(trap)을 포함합니다.
- STOCK 줄기의 mode-0 줄 형식: 실차 `send` 기록에서 확인해야 합니다.
- 에이전트 지시문과 소유자 준비 문서(`OWNER_SETUP_KO.md`).

이 항목이 구현·시험되기 전에는 실행할 수 없습니다. 실행·폰 변경·발행은 별도로 요청받아야 하는 행동입니다.
