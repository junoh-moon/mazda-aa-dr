# GPIO 되읽기와 원본 GPS→제품 MODEL 실행 — 2026-09-30

원본 LDS가 수신기를 선택하지 못하던 VM의 GPIO 되읽기를 분리했습니다.
실험용 QEMU 모델에서 작성한 NMEA를 **원본 LDS가 직접 해석**했고, 그 실제
응답을 원본 BLM 요청·큐·AA 송신과 제품 MODEL 계산까지 연결했습니다.
제품 위치 callback에 합성 기준점을 직접 넣지 않았습니다.

대상은 NA 74.00.324A이며, 제품은 앞서 검증한 `1ccedbf`의 DSO입니다.
이번 `fb7d53a` 분석기 통합까지 제품 runtime 소스는 동일합니다. 차량·폰·동글은
사용하지 않았습니다. NMEA와 센서 입력은 작성한 합성 입력이며, GPIO는 두 핀의
부하 없는 디지털 출력만 모델링합니다. 실제 ASSIST 선택과 지도 반영은 미완료입니다.

## GPIO 원인과 모델

R12에서는 읽기 전용 sysfs·debugfs·MMIO 진단으로 출력 방향과 DR/PSR을
세 시점에서 대조했습니다. 원본 USB 관리자가 전원을 켠 뒤 GPIO3_IO31과
GPIO4_IO15의 DR은 1, GDIR은 출력인데 PSR과 sysfs 읽기는 계속 0이었습니다.
원본 커널의 `mxc_gpio_get`은 PSR을 읽습니다. 앞서 살펴본 `GpioChip.ko`의
가상 VIM GPIO는 이 두 핀의 드라이버가 아닙니다.

원본 커널의 핀 설정에는 두 핀 모두 `ALT5 + SION`이 들어 있습니다.
R13에서는 하드웨어 breakpoint로 원본 store 명령과 레지스터를 읽고 그 명령을
그대로 실행하여 실제 설정 쓰기를 확인했습니다. GDB의 mux 읽기 응답은 `E14`
오류였으며 이를 0이라는 측정값으로 바꾸지 않았습니다. breakpoint는 실행
시점을 바꾸므로 이 실행으로 실제 장치의 시간 특성을 주장하지 않습니다.

QEMU 7.2.22의 출력 PSR 마스킹과 미구현 mux 경로를 보완하는 opt-in 패치를
추가했습니다. 펌웨어 바이트·readiness 응답·GPS 데이터를 변경하는 패치는 아닙니다.
핀 설정, DR과 GDIR이 읽기 값을 결정하며 기본 동작은 비활성입니다.
[모델의 정확한 범위·근거·재현 방법](../docs/QEMU_CMU_GPIO_KO.md)을 따르십시오.

펌웨어 없는 qtest에서 기존 QEMU는 7개 메서드 중 5개에서 총 9개 assertion이
실패했습니다. 출력 되읽기 보완 후 reset 검사 하나가 남았고, 실제 reset callback
등록을 고친 뒤 **7개 모두 통과**했습니다. RESET 사건을 기다리도록 시험도
보강했으며 그 대기만으로 결함이 해결되지 않는 것을 확인했습니다.
최종 검사로 기존 QEMU의 실패도 다시 확인했습니다. 입력 방향·외부 입력,
양쪽 출력값, mux/SION 조건, 다른 핀과 기본 비활성 동작을 포함합니다.

## 원본 실행 결과

각 실행은 helper의 종료 코드 **124**, QEMU 종료 코드 **0**과 완료 표식을
확인한 뒤 로그 해시와 결과를 고정했습니다. 제한 시간 종료나 셸 대기 자체를
PASS로 세지 않습니다. R12–R15는 수신기 진단이며 제품 계산을 실행하지 않습니다.

| 실행 | 조건 | 실제 위치 응답 | 결과 |
| --- | --- | --- | --- |
| R12 | 기존 QEMU, GPIO 레지스터 관측 | 16 | 모두 mode 0 / status 5 |
| R13 | 원본 mux store의 하드웨어 breakpoint 관측 | 16 | 모두 mode 0 / status 5 |
| R14 | 실험용 모델 활성 | 16 | mode 1: 11, mode 0: 5; status 2: 16 |

| R16 | 원본 GPS→제품, 기존 진단 센서 공급 루프 | 24 | mode 1: 17, mode 0: 7; MODEL valid 0 |
| R17 | 원본 GPS→제품, 별도 센서 공급 스레드 | 26 | mode 1: 20, mode 0: 6; MODEL valid 51 |

R14의 UTC·좌표·속도를 실제 공급한 NMEA와 대조했습니다. mode 0인 조회
8–11 뒤 조회 12–15에서 mode 1로 복귀했습니다. 마지막 조회의 mode 0은
공급 종료와 긴 GPIO 진단이 겹친 구간이며 작성한 GPS 무효 구간으로 세지 않습니다.
공급기 338개 문장 세트와 정상 종료를 확인했습니다. 이는 물리 위성 수신이 아닙니다.

**R15의 제한:** 원본이 PTY를 읽지 않아 공급기의 쓰기 assertion이 종료 코드
134로 실패했습니다. 그 전에 유효 플래그를 가진 275개 세트가 공급됐지만
무효→복귀 profile까지 진행하지 못했습니다. 따라서 R14/R15는 기동·GPIO의
비교이며 동일한 전체 GPS 시간표의 비교 성공으로 주장하지 않습니다.

R16·R17은 원본 AA manager가 실제 LDS 요청을 발행하고, 원본 callback·큐·위치
worker·송신을 수행합니다. 요청 목적지와 issue/reply의 연결 수명, 세션 문맥과
실제 send 대상을 기록했습니다. 제품 DSO의 SHA-256·원본 진입 명령 guard를
유지했습니다. 원본 서비스 설정의 진단용 PTY와 부분 SM 그래프, LDS의 관측 전용
추적 preload는 명시적으로 사용하며 정상 차량 전체 기동으로 세지 않습니다.

R16은 진단 센서 공급이 버스 dispatch와 같은 루프에 묶여 있었습니다.
wheel 수신 간격은 최대 **641.849ms**, 150ms 초과는 **16회**였고 유효 MODEL은
없었습니다. 이 결과를 제품 계산 성공으로 숨기지 않았습니다. R17에서는 작성한
공급기만 별도 스레드로 옮겼고 최대 **88.437ms**, 150ms 초과 **0회**였습니다.
제품의 시각·신선도·qualification 조건은 완화하지 않았습니다.

R17의 raw 입력 **1,314개**와 원본 위치 **26개**를 보존했습니다. GPS 무효
구간의 MODEL snapshot **51개**가 valid였고 48바이트 위치 preview를 만들었습니다.
직진 10m/s 입력에 대해 C core의 적분을 재사용하지 않고 WGS84 자오선 거리를
수치 적분·역산하여 비교했습니다. 최대 수치 차이는 `6.33e-9 m`였습니다.
**이는 같은 합성 입력의 계산 일치이며 차량 위치 정확도 수치가 아닙니다.**
GPS 복귀 뒤에는 이 MODEL 유효 결과가 철회됐습니다.

R16/R17의 LOCATION 송신은 각각 **24/26건**, 모두 원본과 같은 48바이트이며
하위 API 반환은 0이었습니다. drop·audit fault·요청/세션/bus 관측 fault는 0입니다.
모든 `assist_ready`는 false입니다. 실제 AA 서비스에는 미시작 세션 요청 거절이
있으므로 하위 반환 0을 폰 수용으로 해석하지 않습니다. 일반 분석은 각각
**inconclusive 27/18**, violation 0입니다.

## 실패·검사 범위·남은 작업

QEMU의 첫 축소 빌드는 공통 ARM TCG에 필요한 ARM_V7M/semihosting 연결이 빠져
링크에 실패했습니다. 해당 Kconfig 선택을 추가한 뒤 빌드했습니다. 초기 reset
실패와 위 R15/R16의 제한도 비공개 기록에 보존했습니다. 첫 결과 집계에서는
같은 위치 call에 속하는 type 21을 LOCATION과 함께 세어 assertion이 실패했고,
원래 LOCATION 계약인 type 1·48바이트로 범위를 바로잡았습니다.

커널 LZO 추출은 뒤쪽 데이터에 대한 trailing-garbage 경고와 종료 2를 남겼습니다.
추출 출력의 크기·커널 주소 배치·exported 심볼과 실제 store 실행을 함께
확인했습니다. 추출 명령이 경고 없이 성공했다고 기재하지 않습니다.

같은 작업 단위의 host Python 330개·C/C++와 고정 ARM journal 12개 검사는
[분석기 통합 기록](MODEL_RESULT_MERGE_2026-09-30.md)을 따릅니다. 이번 GPIO
도구 추가로 제품 ARM 전체 suite를 다시 실행하지 않았습니다. 제품 runtime은
바뀌지 않았으며 새 qtest와 위 원본 실행을 추가했습니다.

**미완료:** 계산 위치의 실제 ASSIST 선택, qualified 센서·provider/receiver/session
연결, 실제 회전·물리 센서 품질, 폰/앱 수용과 정상 차량 기동·복구가 남습니다.
이 실행의 GPS 유효성은 원본 파서의 상태이며 qualified provenance로 승격하지
않습니다. 차량 시험은 요청하지 않으며 공개 ZIP·v1.0 완료 표시는 변경하지 않습니다.

마지막 fetch에서 외부 master `55bdd8feb44ec6a721f05883aef8fd62be0906e8`의
식별자 소진·큐 초기화 수정과 검증 기록을 확인했습니다. 아직 이 작업 브랜치에
통합하지 않았습니다. 위 실행은 그 수정 이전의 고정 제품이며 새 수정의 제품
검증으로 재사용하지 않습니다. 해당 변경의 통합·직접 검증이 다음 작업입니다.
