# 실제 제품과 원본 AA 세션 기동 — 2026-10-02

고정 `8d5669c3cd06180dfcca52758c976c02d7b51b23`의 실제 AA 제품 DSO를
원본 BLM·AA 서비스와 함께 실행했습니다. 원본 IPC를 통한 세션 생성과
해제, 원본 작업 큐의 초기화와 정상 join을 확인했습니다. 이는 실제 제품의
ASSIST 계산부터 원본 LOCATION 송신까지 연결하기 위한 선행 실행입니다.
**이번 실행에는 위치 callback·DR 계산·LOCATION 송신이 없습니다.**

## 실행 조건

NA 74.00.324A의 제공된 원본 라이브러리·AA 서비스와 해당 제품을 사용했습니다.
기존 고정 GCC 4.9.1, ARM user-mode QEMU와 원본 userspace 라이브러리에서
실행했습니다. 커널 syscall은 시험 호스트가 처리하므로 원본 CMU 커널이나
정상 전체 SM 기동의 재현으로 세지 않습니다.

작성한 호출기가 cold 설치 시점을 확보한 뒤 실제 제품 설치기를 호출합니다.
원본 다섯 모듈의 해시, 데이터 슬롯 21개와 진입 패치 네 개를 확인합니다.
이후 원본 singleton·DBus 초기화·WorkerQueue·VehicleDataManager·RaceAap의
실제 함수를 호출합니다. 시작 순서는 작성한 조건이며 제품 자동 bootstrap의
실행 증거는 아닙니다. 제품 코어를 호출기에 소스 링크하거나, 수동 위치
callback·WorkerScope·송신 성공 대체 함수를 넣지 않았습니다.

원본 설정 두 개와 필요한 인증 파일 다섯 개는 비공개 경로에서만 사용하고
전후 해시를 대조했습니다. 본문·원본 바이너리·역어셈블리는 공개하지 않습니다.
별도 서비스/HMI 버스, 작성한 파일 경로와 종료 기한을 사용했습니다.
차량 장치나 폰은 연결하지 않았습니다.

## 첫 실패와 환경 대조

첫 `original-startup-r1`에서 원본 서비스는 SysV 큐 두 개를 만들었지만,
122,880바이트로 늘리는 `IPC_SET` 두 번이 `EPERM`으로 실패했습니다.
서비스는 종료 1이고 제품 호출기는 시작하지 못했습니다. 당시 전용 컨테이너의
`kernel.msgmnb`는 16,384였습니다. 최초 오류 문구가 큐 생성 전 종료처럼
표시됐지만 실제 syscall에서는 두 큐의 생성을 확인했으며 실패 기록을 보존합니다.

호스트와 기존 컨테이너를 그대로 두고 새 private IPC namespace에서 한도만
122,880으로 맞췄습니다. 작성한 native·ARM 대조에서 큐 설정은 성공했으나,
원본과 같은 mode 0000의 송수신은 둘 다 `EACCES`였습니다. mode 0600 대조는
성공했습니다. 이어 `CAP_IPC_OWNER`만 추가한 전용 컨테이너에서는 두 아키텍처의
두 mode, 총 네 대조가 실제 설정·송신·수신·제거를 완료했습니다.
`CAP_SYS_RESOURCE`나 privileged 모드는 사용하지 않았습니다.

실패한 시스템 호출을 성공으로 대체하거나 원본의 큐 권한을 바꾸지 않았습니다.
환경 준비 중 작성한 명령 인자와 검사 가정의 오류도 첫 기록을 보존한 뒤
정정했습니다. 종료된 namespace 번호 재사용은 살아 있는 호스트/시험 namespace의
동일성과 구분했습니다. 호스트·기존 컨테이너의 sysctl은 변하지 않았습니다.

첫 원본 실행에서는 stdout이 종료 때 한 번에 기록됐으며 준비 단계에는
도달하지 못했습니다. 실행 중 준비 문구를 관측하기 위해 작성한 프로세스의
버퍼링 대조를 검사하고, 후속 호출기는 stdout만 private PTY로 수집했습니다.
실제 준비 문구와 큐 세 개를 함께 확인하며 원본 libc 함수를 대체하지 않습니다.
leader 종료 후 남는 자식의 bounded cleanup 회귀도 별도로 검사했습니다.
이 준비 검사를 제품 실행 횟수에 합산하지 않습니다.

## 후속 원본 실행

같은 제품의 `original-startup-r2`는 다음 경로를 완료했습니다.

1. 실제 cold 설치 성공, 원본 해시·슬롯·진입 패치 대조.
2. 원본 BLM 작업 큐 초기화와 큐에서 실행한 manager 초기화.
3. 원본 AA 서비스의 IPC 응답에 의한 실제 세션 생성과 제품의 lifetime 관측.
4. 남은 요청·worker 0 확인, 원본 세션 해제.
5. 원본 manager·DBus 해제, 작업 큐 stop·join 0, 호출기 종료 0.

원본 큐 작업 네 개의 post·시작·완료를 확인했습니다. syscall 원문에서 서비스
및 호출기의 실제 IPC 설정·송신과 수신을 확인했습니다. 일부 다중 스레드
출력이 섞인 수신 행의 개별 반환값은 추정하지 않았습니다.

독립 검토자는 재실행 없이 원문·제품 pin·원본 다섯 해시·작성 호출기의 검사·
입력 149개와 비공개 설정 일곱 개를 다시 대조했습니다. 최종 IPC·소켓·별칭·
실행 프로세스 잔여는 0입니다. 원본 AA 서비스 프로세스 자체는 클라이언트의
정상 세션 해제 후 시험 소유자가 SIGTERM으로 종료했습니다. 이를 전체 OEM
서비스의 정상 종료나 차량 전원 복구 성공으로 표현하지 않습니다.
