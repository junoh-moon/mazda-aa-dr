# VIP 이미지에서 복원한 차량 모션 신호의 CAN 지도 — 2026-10-03

CMU가 받는 차속·휠 속도·yaw·가속도의 **원본 CAN ID와 비트 배치**를 차량 없이 펌웨어에서
복원했다. 서브에이전트가 업데이트 패키지의 VIP(M16C 마이크로컨트롤러) 이미지를 정적 분석했다.
이미지 `vip/e0000000002.dat`(`image-vip_appvfbl.mot`)의 SHA-256은
[VIP 누적기 기록](VIP_ACCUMULATOR_2026-10-01.md)의 값과 같다(버전 문자열
`VIP_APP-MAZ150_10.13.012`, `VIP_CAN-MAZ140_07.09.020`). 기존 기록은 VIP가 만드는 SPI 패킷의
합계·개수 의미를 다뤘고, 이번에는 그 앞단인 **CAN 수신 설정**(메일박스·해시 표, 메시지별
DLC·버퍼·콜백)을 처음 읽었다. 정적 분석이며 이미지를 실행하지 않았다. 원본 이미지와 디스어셈블
덤프는 싣지 않는다.

신호 경로: 차량 CAN → VIP(채널 1 = CMU가 "Public CAN"이라 부르는 차량 버스) → SPI →
`vim_app` → VIMC → `jciVBS`의 `libjcimod_can.so` 처리기 → VDT/VDM → SMDB.

## 수신 프레임과 VIP가 꺼내는 필드 (채널 1, 빅엔디안)

| CAN ID | DLC | 필드 |
| --- | --- | --- |
| **0x215** | 8 | 바이트 0-1, 2-3, 4-5, 6-7의 u16 네 개(휠 속도). 공개된 openpilot `WHEEL_SPEEDS`와 같은 배치. 어느 바퀴인지는 펌웨어에 표기가 없다. |
| **0x078** | 6 | 바이트0 상위 2비트 Qf. 종가속도 13비트(바이트0 하위 6비트+바이트1 상위 7비트). **yaw 12비트**(바이트1 최하위 비트+바이트2+바이트3 상위 3비트). 브레이크 압력 13비트(바이트3 하위 5비트+바이트4). 바이트5 상위 2비트 Qf. |
| **0x079** | 2 | 바이트0 상위 2비트 Qf, 횡가속도 13비트. |
| **0x202** | 7 | 바이트 2-3 차속. 바이트 0-1의 상위 13비트 엔진 회전수. 바이트1 하위 2비트 상태(VIP는 값이 3일 때만 속도 사용). |
| **0x09F** | 7 | 바이트0 하위 3비트가 SPI 0x118로 전달된다. 레포가 후진으로 보는 필드. |
| **0x240** | 8 | SPI 0x119로 전달(조향 처리기 `VBS_BUS_CAN_EPAS_Control`). |
| 0x086 | 6 | 수신하지만 바이트 0-1은 쓰지 않는다. SPI 전달도 찾지 못했다. |

VIP가 만드는 SPI: **0x100**(휠 네 개, 창 평균), **0x116**(yaw 합계·개수, 종가속도, 브레이크
압력, Qf 두 개), **0x169**(횡가속도), **0x15B**(차속·엔진 회전수, 값이 바뀔 때만 전송),
0x118(0x09F), 0x11C(속도 임계 플래그). **현재 레포의 0x116 파서는 +1..+3(yaw 합계·개수)만
사용한다**; +4..+9의 종가속도·브레이크 압력·Qf는 쓰지 않는다.

yaw 한 카운트는 약 0.0377°/s(0.000658615 rad/s)이고 범위는 약 ±77°/s다. 기존 SMDB 계약
`(raw−2047)/약 −26.5`와 같은 값이다. yaw에는 자체 Qf가 없다.

## 공개 해독과의 대조

- 0x202 차속(바이트 2-3, `raw/360 m/s`): **일치**. 레포의 기존 계약, RaceChrono ND 해독, ND DBC와 같다.
- 0x215 휠 속도: ND 계열의 수신 ID이고 배치는 openpilot과 같다. 단위는 레포의 기존 NNG 계약(0.01,
  0점 10000)을 따른다.
- 0x078의 브레이크 압력: 펌웨어(바이트3 하위 5비트+바이트4)는 RaceChrono ND 해독(비트 28부터 12비트)과
  비슷한 위치이고, berumiya의 ND DBC(바이트 4-5 16비트)와는 다르다. 비트 수준에서는 DBC가
  불완전하다고 보고 **CMU 입력 정의는 펌웨어를 우선한다.** DBC는 yaw를 0x79·0x75에 둔다.
  펌웨어가 읽는 12비트 yaw는 0x078 안에 있어 서로 일치하지 않는다.
- 0x5A(횡가속도 작업 중 해독): CMU 수신 표에 **없다.** CMU는 횡가속도를 0x079에서 받는다.
- 0x086 조향각: VIP가 쓰지 않는다. CMU의 조향 신호는 0x240에서 오는 것으로 보인다(추정).

## 추정 (입증하지 못함)

- 휠·yaw 창은 약 100 ms이며(RTOS 1 ms 틱 가정), 평균 표본은 CMU 도착 시 최소 약 50 ms 지났다.
  틱 설정을 찾지 못했다.
- 2비트 Qf는 Ford식(3 = 정상, 0 = 고장)일 가능성이 높다. CVD의 qf 0 → 65535 매핑과 맞는다.
- 가속도 0점·배율(0x078의 13비트 0점 8000, 1952 카운트/G 정도)은 공개 DBC 주석으로만 뒷받침된다.
- 0x09F 바이트0 하위 3비트가 후진등인지 기어인지 모른다.
- CMU의 Public CAN이 HS-CAN 그대로인지 게이트웨이 사본인지 펌웨어로는 알 수 없다.

## 제품에 주는 제약

- 생산자 시각이 없다. 창 길이 약 100 ms는 추정이다.
- 8비트 개수와 16비트 yaw 합계는 넘칠 수 있다(MODEL이 이미 다룬다).
- 잘못된 휠 프레임은 조용히 버려지고, 40000(300 km/h) 초과 평균이면 이전 값이 표시 없이 재전송된다.
  SPI 큐 적재가 실패하면 그 창이 조용히 사라진다.
- 0x15B 차속은 값이 바뀔 때만 오므로 시간 기준으로 부적합하다.

## 실제 주행 데이터로만 풀리는 것

yaw 부호와 편향(공칭 2047), 휠 순서와 타이어 배율, 실제 프레임 주기와 VIP 창 길이, 종단 지연, 6MT의
후진 필드 값, 가속도 배율·부호, 이 ND2가 0x078·0x079를 실제로 송신하는지. 이 기록은 설계 변경이나
live ASSIST 활성화를 승인하지 않는다.
