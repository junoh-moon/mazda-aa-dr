자격 상실, 새 GPS 기준점 이후 재개, inline 출처 거부를 연결했습니다.
GDB 없는 최종 실행은 POSITION/LOCATION 18쌍, DR 대체 6건과 최종 GPS 원본

배포 ASSIST 활성화의 완료로 세지 않습니다.

## 최종 실행

`original-recovery-r2`는 원본 LDS reader·응답, BLM callback·작업 큐,
실제 제품 AssistWorker와 원본 `aap_send_vehicle_data`를 실행했습니다.
원본 callback·sender를 대체하거나 후보를 직접 발행하지 않았습니다.

| 구간 | 실제 LOCATION 호출 | 확인한 동작 |

| 두 번째 단절 | 12–15 | 첫 단절 전달 후 DR 3건 재개 |
| inline 출처 거부 | 16 | 같은 generation의 유효 후보가 있으나 BAD_PROVENANCE로 원본 전달 |

입력 508개는 실제 source pop 수·worker 소비 수와 일치하며 BEGIN은 2개입니다.
후보 발행 133회, 서로 다른 계산 frontier 70개를 확인했습니다. 독립 WGS84
적분·UTC·속도·방향·기한 검사와 실제 대체 48바이트 비교를 통과했습니다.
최대 좌표 차이 약 `1.06e-7 m`는 작성한 입력 모델끼리의 수치 차이입니다.
물리 위치 정확도나 133개의 서로 다른 센서 측정을 뜻하지 않습니다.

호출 16의 원본 POSITION 사본은 SEND 뒤 실제 worker 상태 확인까지 작성
공급부에서만 보류했습니다. 원본 callback·SEND는 기다리지 않았습니다.
보류 중 센서 창·watermark를 앞질러 진행하지 않았고, 거짓 출처의 사본을
수정 없이 SEND 약 55.58 ms 뒤 전달했습니다. 실제 소비 순번 408에서
INPUT_FAULT·철회가 기록됐습니다. 후보의 generation·기한과 전후 worker의
PUBLISHED 상태·철회 수를 함께 확인하여 단순 거부 코드와 구분했습니다.

client와 LDS reader/server는 종료 0, 원본 요청 배출·세션 해제·큐 join,
제품 capture.done을 완료했습니다. AA 서비스와 monitor는 실행 관리자가
SIGTERM으로 종료했습니다. 원본 AA 서비스의 세션 상태 거부는 남으므로
로컬 송신 반환 0을 정상 서비스 처리나 폰 수용으로 해석하지 않습니다.
비대체 LOCATION 12건은 48바이트가 원본과 같습니다.

앞선 `original-recovery-gdb-r3`도 18쌍·대체 6건·BEGIN 2회로 완료됐습니다.
입력은 511개, 발행은 132회이며 중간 debugger 정지는 없었습니다.
GDB 연결 자체의 영향을 배제하지 않아 GDB 없는 최종 실행과 구분합니다.

## 보존한 실패와 판정기 수정

- 첫 recovery는 철회 이후 위치 요청 진행이 멈춰 실패했습니다.
- GDB 첫 시도는 QEMU가 MI 중단 요청에 응답하지 않아 스택을 얻지 못했습니다.
  작은 작성 ARM 프로그램에서도 재현한 뒤, 소유 QEMU에 SIGINT를 보내
  ARM 스택·레지스터를 읽고 guest에 신호를 전달하지 않고 재개하는 대조를
  확인했습니다. 원본 함수·메모리·반환값을 바꾸지 않았습니다.
- GDB 두 번째 시도는 새 GPS 이후 진행이 멈췄으며 실제 ARM 스택을 얻었습니다.
  한 스레드는 D-Bus poll에 있었고 작업 큐는 빈 대기 상태였습니다. 원본 control
  호출의 `-1`은 기본 25초이며 무기한 상수가 아닙니다. daemon은 오류 응답을
  이미 보냈지만 local pending 처리 완료 여부는 확정하지 못했습니다.
  작성 fixture의 7초 기한에서 끝났으므로 원본의 25초 만료도 확인하지 못했습니다.
- 후속 두 성공이 이 간헐적 대기의 원인 해결을 증명하지는 않습니다.

독립 리뷰에서 발견한 판정기 허점 11개를 각각 실패 대조로 재현하고 고쳤습니다.
각 후보는 그 상태를 읽은 동일 worker callback의 실제 소비 prefix와 BEGIN
수로 계산합니다. inline 전후 generation·상태, 실제 전달 기한·소비 순서와
해당 입력에서의 fault를 검사합니다. 수정 후 기존 반례와 정상 시각 경계
20건을 독립 대조했습니다. Python 판정기 검사는 제품 실행 개수에 합산하지 않습니다.

두 성공 실행을 다시 읽어 각각 입력 158개를 재해시하고, 원본 monitor·제품
sideband·POSITION 18쌍의 정확한 요청 키와 숫자 162개를 대조했습니다.
