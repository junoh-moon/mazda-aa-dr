## 실행 결과와 최초 실패

최종 전체 host 재실행은 Python 375개와 C/C++를 통과했고 생략은 0입니다.
고정 ARM 전체는 한 실행에서 종료 0·생략 0입니다. 시작/끝의 다섯 바이너리,
도구체인 입력이 같고 `release_verified=true`입니다. 실제 제품 DSO의
position 8·request 14·wire 1·session 29·bus 31·assist 23·runtime-assist 9개를
포함합니다. 순정 공유 runtime에서 최종 wire 1·assist 23·runtime-assist 9개도
별도 통과했습니다. wire 한 사례는 여러 호출·수명·예외 경계를 함께 검사합니다.

첫 host 전체 실행은 ARM과 동시에 진행하던 중 합성 motion 송신의 EAGAIN으로
100ms 재시도 한도를 소진했습니다. 재시도는 95회이며 fixture의 `received_ns`부터
실패 기록까지는 100.963ms입니다. 실패한 값은 정상 REVERSE
입력이며 의도한 오래된 두 입력은 이미 각각 receipt/transport 경계 사유로
기록됐습니다. 잔존 파일에는 미완성 JSON 행이 있고 `capture.done`은 없었습니다.
앞선 정상 health 표본은 실패 순간의 원인을 설명하지 못합니다.

같은 코드·바이너리·100ms 기한의 단독 재실행은 원시 530건을 모두 수락했고,
그 뒤 전체 host도 통과했습니다. 기한·제품 로직을 바꾸지 않았습니다.
최초 실패와 잔존 원본을 보존했으며 CPU 부하·I/O·계산 지연 중 어느 원인인지는
미확정입니다. 재실행 성공으로 최초 실패를 지우거나 차량 부하 검증으로 세지 않습니다.

ARM runtime worker의 철회 검사는 500ms 안에 명시적 NOT_READY 사유를 확인한
범위입니다. host의 140/150ms 발행 기한 만료 전 철회 검사와 구분합니다.
외부 입력 fixture의 core 순번 할당도 실제 qualified 공급부 구현을 뜻하지 않습니다.

## 원본 모듈과 최종 ZIP

최종 DSO를 startup preload하고 실제 cold installer를 실행했습니다. 원본 파일
해시 다섯 개, GOT 20개와 코드 진입점 네 개를 확인했습니다. 원본
`LDS_DATA_GetPosition` 네 요청에서 같은 본문의 역순 응답 두 개, 오류 한 개,
미응답 요청의 connection-free 취소를 검사했습니다. 요청·worker·관측 loss는
종료 시 0이며 별도 server·bus monitor와 대조했습니다. 서버와 즉시 worker
소비는 작성한 fixture입니다. 새 검사에서 원본 LDS producer·전체 BLM WorkerQueue·
SM 기동을 실행했다고 확대하지 않습니다. 29요청 검사는 앞선 wire 기록의 별도 실행입니다.

최종 ZIP을 그대로 풀어 순정 ARM BusyBox 1.19.2/libc에서 손상 묶음 거부,
설치·두 DSO loader·일회 기동 가드·collector UID/종료·숫자 메뉴의 상태·종료·
USB 회수·제거·재설치를 통과했습니다. 실제 15초 종료 미확인 뒤에도 원본 회수와
별도 실패 상태를 남기는 경로, 잘못된 USB 경로도 검사했습니다. 마운트 상태와
센서·health 행은 작성한 fixture이며 실제 차량 파일시스템 시험이 아닙니다.
최초 준비 스크립트의 증거 폴더 소유권 오류는 binfmt 등록 전에 발견했고,
제품 변경 없이 별도 실행 디렉터리에서 검사를 완료했습니다.

태그의 commit object를 GitHub API로 확인하고 ZIP·체크섬 두 파일을 초안에서
검사한 뒤 게시했습니다. 공개 파일을 새 디렉터리에 내려받아 로컬과 바이트
동일성, 외부 SHA·CRC·전체 manifest, SHADOW·소스 상태·다섯 제품 해시를 확인했습니다.
소스 입력 87개도 태그의 Git object와 대조했습니다. OEM 바이너리·maps·원본
위치 로그는 첨부하지 않았습니다. 설치 명령과 숫자 메뉴는 이전 판과 같습니다.

## 도구 제거와 남은 과제

작업용 컨테이너의 추가·갱신 패키지 79개 행, 고정 도구체인 2,124파일,
임시 펌웨어 추출본·별도 checkout·진단 daemon을 제거했습니다. 최종 ARM 증거
598파일과 DSO 결과 JSON 일곱 개는 삭제 전에 해시 대조해 비공개 보존했습니다.
작업용 binfmt·helper·호스트 QEMU 복사본은 ZIP 검사 직후 제거했습니다.
기존 Docker 이미지는 유지했고 호스트 패키지·이미지·컨테이너·binfmt 목록은
최초 상태와 같습니다. 호스트 패키지 설치나 `sudo` 실행은 없었습니다.

실제 관성항법 적용은 아직 완성되지 않았습니다. LDS 필드별 producer→snapshot→
응답 자격, 물리 센서의 시각·단위·품질, 반복 부하의 지연 원인, 차량 복구와
Galaxy S25/지도 앱 수용이 남습니다. 다음 펌웨어 실험은 GGA/RMC 각각의 원본
캐시 갱신과 실제 server snapshot을 요청 token에 연결하는 것입니다. 현재는
조사만 했으며 구현·실행하지 않았습니다. live ASSIST를 이 결과로 활성화하지 않습니다.
