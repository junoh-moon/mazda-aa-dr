# G3 저장 요청 시점 추적과 실차 방위 없는 기록의 원인 — 2026-10-28

**결론: [G3 재생 진단](G3_REPLAY_DIAGNOSIS_2026-10-28.md)의 방위 없는 정차 S 14건은 주로 재생 입력 부족에서 생긴 결과입니다. 실차 저널에서는 대부분의 S 기록에 방위가 있습니다. 실차에서 다음 부팅의 복원을 `no_heading`으로 막은 기록 2건 중 1건은 정차 중 AA cadence fence가 rule F taint를 미확인 종료시킨 의도된 안전 재기록으로 판단되며, 다른 1건은 미확정입니다. 기본 설치에서 G3를 막는 주된 원인은 여전히 `age_unknown`(CMU 시계)입니다. 제품 소스·기본값·공개 릴리즈는 바꾸지 않았습니다.**

## 1. 무엇을 추가했는가 (재생 전용)

- `tools/replay_beta.cpp`에 `--g3-request-out FILE`을 추가했습니다. tracker가 저장 요청(S/M 기록 또는 token)을 내주는 tick마다 JSON 한 줄을 씁니다. 내용은 요청 시각, 요청한 기록의 상태와 heading 플래그, 그 시점 G3 sample의 BETA 방위 유효 여부, 부팅 내 최초·최종 유효 시각, 유효→무효 전이 횟수와 원인(`reset`/`unseeded`/`core_reason`/`budget`), yaw 사슬 break 수와 원인별 분류(pipeline reset, rule F discard, 이동 중 yaw 공백), 이동 시간·거리, BETA anchor 관문별 누적 수입니다.
- 관찰 전용입니다. pipeline·tracker 판단을 바꾸지 않고, window child에서는 쓰지 않습니다. 제품 G3 저널 형식은 바뀌지 않습니다.
- 시험 `tests/replay/test_replay_g3_request.py` 3개를 먼저 작성해 RED(옵션 없음, exit 2)를 확인했습니다. 구현 후 첫 실행에서 무GPS 픽스처가 S 대신 lazy token 요청만 낸다는 것을 확인했고, 해당 시험의 기대를 그 사실에 맞게 고쳐 GREEN이 됐습니다. 시험은 시드된 주차, 시드 없는 부팅(모든 anchor `BAD_FIX`), 옵션 유무에 따른 CSV·BETA 저널·G3 저널 동일성(호스트 I/O 시각 제외)을 확인합니다.

## 2. 실제 21부팅 재실행

- 기존 `commands.json`의 `--g3-send on` 계열 21개를 새 `build/replay_beta`, 빈 저장소, 원래 순서로 실행했습니다. 14개 exit 0, 7개 exit 2(adapter POSITION 없음)로 기존과 같습니다.
- 재생한 14개 부팅의 CSV·BETA 저널·송신 기록은 10-28 진단 실행과 바이트가 같습니다. G3 저널은 `start_ns`/`end_ns`/`lat_ms`를 빼면 같습니다. 처음에 `--g3-send off` 계열로 대조해 송신·G3 저널이 달랐습니다. 이는 계열이 달랐기 때문이며, 같은 계열로 다시 돌려 일치를 확인했습니다.
- 출력은 Git 제외 경로 `private-data/g3-request-20261028/`에 있습니다.

## 3. 재생 입력은 실차 판단의 일부만 담습니다

같은 부팅의 BETA anchor 기록 수를 실차 저널과 재생 저널에서 비교했습니다.

| 부팅 | 실차 anchor | 재생 anchor | 실차 ACCEPTED |
|---|---:|---:|---:|
| 01 | 3,174 | 174 | 2,876 |
| 03 | 1,372 | 121 | 1,053 |
| 11 | 3,797 | 116 | 3,707 |
| 17 | 3,219 | 178 | 2,705 |
| 18 | 4,365 | 201 | 3,929 |
| 20 | 1,385 | 300 | 1,104 |

재생 BETA가 받는 POSITION은 실차의 약 3–22%입니다. 지속 로그가 POSITION을 일부만 보존하기 때문입니다. 실차 상태 전이도 다릅니다. boot 01의 실차는 3253 s 상실 → 3358 s `core_rejected` 철회였고, 재생은 3284 s `sensor_silence`였습니다. 따라서 **재생의 시드 부재·reset 사슬은 실차 동작이 아닙니다.** 10-28 기록의 "복원 14회 중 `no_heading` 11"을 실차 G3 실패율로 읽지 마십시오. 그 기록의 수치는 고치지 않고 이 문단으로 해석 범위를 정합니다.

## 4. 실차 저널이 직접 보여 주는 것

두 비공개 내보내기(cmu-20261017, cmu-20261025)의 실차 `g3_store` 행을 부팅별로 모았습니다. 실차 DSO는 beta.15/16 공용이며 garage carry 규칙이 아닙니다([NEW_EXPORT_2026-10-25](NEW_EXPORT_2026-10-25.md)).

- 방위가 있는 기록은 대부분 성공적으로 저장됐습니다. 예: 41945267은 S 22건 중 21건, 08375179는 22건 중 20건에 방위가 있습니다.
- 다음 부팅의 복원 결과는 다음과 같습니다.

| 복원 결과 | 부팅 수 | 의미 |
|---|---:|---|
| 방위 있는 기록 적재, `CARRIED_UNVERIFIED age_unknown` | 4 | 그중 3개는 이후 `unc_grew`로 REJECTED |
| `no_heading` 거부 | 3 | 앞 부팅의 마지막 기록 2개에서 비롯 |
| `unc` 거부 | 1 | |

### 사례 A: 41945267 (다음 두 부팅이 `no_heading`)

- 3882.7 s에 방위 있는 S(seq 31)를 저장했습니다(`m_b` 23879.7).
- 정차 중 `beta_cadence_fence`가 두 번 일어났습니다. 3915.4 s는 send 간격 3005 ms, 3916.0 s는 position 간격 3028 ms로, 둘 다 한도 3000 ms를 넘었습니다.
- 3927.8 s에 60 s 정차 fsync 재기록(seq 32, `sync` 1, `wait_s` 45)이 **방위 없이** 기록을 덮었습니다. `m_b`는 23879.7 그대로이므로 **차는 움직이지 않았습니다.**
- 코드상 cadence fence는 `fence_beta()` → `reset_beta()` → `end_assumed_origin(false)` 경로를 탑니다. G3 사슬 break는 BETA 시드가 rule F(전진 가정)에서 왔을 때만 생기며, 이때 `discards`도 함께 늘어납니다. 그 구간에 pipeline reset 행은 없고 차는 정지해 있었으므로 이동 중 yaw 공백도 해당하지 않습니다. 따라서 이 덮어쓰기는 [rule F taint 설계](G3_FIRST_DRIVE_2026-10-11.md)의 의도된 재기록으로 판단합니다. `discards` 값은 실차 저널에 없으므로 **배제에 의한 판단**이며 직접 관측은 아닙니다.
- 덮어쓴 시점에 그 부팅은 약 3,900 s 동안 실차 ACCEPTED anchor 3,707개를 받았습니다. 그런데도 시드가 rule F taint 상태였다면, 0x118 실제 전진 확인이 한 번도 없었다는 뜻입니다.

### 사례 B: 5a9f9b2b (다음 부팅이 `no_heading`)

- 2483.0 s에 방위 있는 S(seq 9)를 저장했습니다.
- 그 뒤 주차 기동으로 12.2 m를 움직였고, 2520.5 s에 cadence fence가 send·position 모두 3044 ms 간격으로 일어났습니다.
- 2526.4 s에 방위 없는 S(seq 10)를 저장했고, 이후 2582.9 s, 2628.0 s의 기록도 방위가 없습니다.
- 그 구간의 원시 바퀴 이벤트가 보존되지 않아 fence가 마지막 움직임 전인지 후인지 가릴 수 없습니다. **미확정**입니다.
- 같은 부팅에서 2026.7 s의 `BAD_INPUT` reset으로 reverse latch가 지워진 뒤, 약 6분 동안 anchor가 모두 `REVERSE` 관문에서 거부됐습니다. 그동안 S 3건에 방위가 없었습니다. 다만 마지막 기록에는 직접 영향을 주지 않았습니다.

## 5. 판단

1. 재생의 방위 없는 기록 대부분은 입력 부족에서 생긴 결과이며 제품 결함의 증거가 아닙니다. 재생으로 G3 저장 품질을 판정하려면 실차가 평가한 POSITION 전체가 필요합니다. 기존 내보내기로는 불가능합니다.
2. 실차의 `no_heading` 원인 1건은 안전 규칙(rule F taint)이 의도대로 동작한 결과입니다. 다만 같은 미확인 방위가, fence가 없었다면 디스크에 남아 다음 부팅으로 이월됐을 것입니다. 무관한 AA 주기 지연이 결과를 가른다는 비대칭이 있습니다. 이 규칙을 바꾸는 것은 안전 규칙 변경이므로 사전 등록 시험과 소유자 결정 없이 하지 않습니다. 가능한 후보로는 "정차·무이동 중 fence는 taint를 끝내지 않음"이나 "지속 전진 속도 증거로 taint 해제"가 있습니다. 둘 다 구현하지 않았고 검증되지 않았습니다.
3. 이것을 고쳐도 **기본 설치의 G3 화면 동작은 바뀌지 않습니다.** 실차 복원 9건 중 4건은 방위 있는 기록을 적재하고도 `age_unknown`으로 송신 창이 열리지 않았습니다. 그 벽을 넘는 경로는 기본 꺼짐인 garage carry(`chain_depart`)뿐입니다.
