# 원본 RMC의 빈 방위각과 실제 AA 응답 — 2026-10-02

원본 reader에 방위각이 빈 RMC 문장을 넣으면, 이번 두 작성 입력에서는
파서가 성공을 반환하고 방위각을 0으로 대입했습니다. 실제 LDS 제품은
이를 새 쓰기로 기록했고 같은 값이 원본 응답과 AA 송신까지 전달됐습니다.
**새 할당 번호와 숫자 0만으로 실제 북쪽 방위각과 입력 누락을 구분할 수
없습니다.** 두 이력에서 같은 결과가 나왔다는 관측이며, 모든 파서 입력이
이전 상태와 무관하다는 결론은 아닙니다.
명시적인 course 0 문장은 이번 원본 실행의 대조군에 포함하지 않았습니다.

## 고정 조건과 실행

제품 소스는 `3625449ba1cd713c4b7ce13f778847acd86d8819`입니다.
AA DSO SHA-256은
`9e248620c8f046586480f9e55b6f41819f75e12ca386cd99498d4a4dddcbce10`,
LDS DSO는 `2da6112779140af2760520e2143e56b2f4bcbdc18aa75a10f1abe997b6a4cff0`입니다.
앞서 검증한 여섯 제품을 변경하지 않았습니다.

서로 다른 원본 reader 프로세스와 bus GUID로 A/B를 각각 한 번 실행했습니다.
동일한 GSA/GGA 준비 뒤 방위각만 20도·40도로 다른 정상 RMC를 주고,
두 실행 모두 동일한 빈 course RMC, 정상 70도 RMC, checksum만 손상한
빈 course RMC를 차례로 보냈습니다. 입력은 작성한 PTY 문장이며 실제
차량 센서나 폰을 사용하지 않았습니다.

원본 reader가 직접 parser와 callback을 호출했습니다. 제품은 기존의
자동 preload·27개 hook 설치·원본 응답·실제 AA inline 조회 경로를
사용했습니다. 별도 진단 parser/select 관측 두 곳은 인수와 원본 호출,
반환·errno를 보존하고 Close 뒤 복원했습니다. 다음 select 관측은 읽기
배치 완료일 뿐이며 callback 선택은 새 실제 제품 쓰기와 별도로 대조했습니다.
관측기 시각은 입력·조회 순서를 검사하는 로컬 시각이며 측정 시각이 아닙니다.

## 저장 자료에서 확인한 결과

| 단계 | A 방위각 | B 방위각 | 원본 parser 반환 | heading 쓰기 번호 |
| --- | ---: | ---: | ---: | ---: |
| 정상 seed | 20 | 40 | 0 | 3 |
| checksum 정상, course 비어 있음 | 0 | 0 | 0 | 4 |
| 정상 course 70 | 70 | 70 | 0 | 5 |
| 빈 course 문장의 checksum 손상 | 70 유지 | 70 유지 | 14 | 5 유지 |

선택한 여덟 응답은 입력 처리 뒤부터 다음 입력 전 사이에 발행됐으며,
여섯 필드의 wire 식별자로 원본 응답·sideband·실제 AA inline 사본을
대조했습니다. 모두 `matched_locked_for_send`였고 원본 LOCATION의
48바이트 송신 내용을 보존했습니다. 입력을 썼다는 사실이나 값의 일치만으로
요청을 연결하지 않았습니다. checksum 손상도 실제 parser 처리와 반환을
관측했으며, 시간 초과를 입력 거부의 근거로 사용하지 않았습니다.

전체 A 실행은 POSITION/LOCATION 10쌍·원시 필드 90개, B는 11쌍·99개를
대조했습니다. 전체 inline match는 각각 8개이고 unavailable은 2개·3개입니다.
선택한 네 단계씩의 여덟 응답과 전체 21쌍을 구분합니다. 각 실행의 최초
worker 시작 전 sideband 한 건은 의도적으로 없었습니다.
실제 client/server와 두 launcher는 모두 종료 0입니다.

## 검증기·실패·정리

검증기를 먼저 실패시키고 보강했습니다. 늦은 다른 단계 응답, 폴더명으로
구분한 가짜 프로세스 수명, 다른 setup·fixture, 0번 할당 출처 등을 거부하는
native 검사 네 개와 그 안의 음성 변형 20개를 통과했습니다. 별도 파일
집합 검사 두 개는 두 캡처에서 같은 파일을 빼도 성공하던 허점을 막았습니다.
실행 manifest에서 도출한 작성 입력 16개의 이름·해시 전체가 A/B에서 같습니다.
이 native 검사는 원본 펌웨어 실행 횟수에 포함하지 않습니다.

첫 ARM 시험 코드 컴파일의 `std::snprintf` 호환성 실패를 보존하고 수정했습니다.
후속 컴파일 및 관측 clock 실패 처리 보강의 컴파일은 통과했습니다.
정적 검토·판정기 검사와 실제 원본 A/B 실행을 별도로 기록합니다.

저장 원문을 독립적으로 읽어 parser 반환, 여덟 실제 POSITION/SEND,
선택 순서와 새 쓰기 번호를 대조하고 각 실행의 원문 여섯 파일과 작성 입력
16개를 다시 해시했습니다. 원본 실행은 반복하지 않았습니다.
각 실행은 소스 416개·제품·도구·원본 archive의 불변을 기록했습니다.
소유 프로세스·IPC·socket·전역 alias를 정리하고 비공개 산출물 314개는
내용·mode·mtime을 유지하며 소유권만 복원했습니다.

A/B trace SHA-256은 각각
`1bf0dcddea2f0b5f5797ec83a4f178f4cd375d2020fb20715bae19947c14c0fd`,
`5cdbb4d0c36baaa0dc6427cb807301ee119dd445baa5867bc6aa62e5a0c90ba2`입니다.
원본 바이너리·진단 dump와 전체 비공개 캡처는 공개하지 않습니다.
제품 소스가 같으므로 전체 host/ARM suite를 새로 실행한 결과로 세지 않습니다.

## 다음 제품 경계와 한계

존재 정보가 없습니다. 다음 구현은 알 수 없음·빈 token·존재하는 token을
구분하여 검증된 실제 callback·cache 쓰기에 연결하는 것입니다. **이 후속
제품 기능은 이 기록 시점에 미구현입니다.** 빈 course도 실제 대입이므로
기존 heading 쓰기 mask를 지워 문제를 숨기지 않습니다. token이 있다는
사실도 숫자 유효성·수신기 품질·물리 측정 시각의 자격을 주지 않습니다.
