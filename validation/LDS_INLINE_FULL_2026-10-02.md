# LDS inline 연결 제품의 전체 검사 — 2026-10-02

고정 소스 `01cb9395d9ba95e3ae7fe493266600e3709bffc9`에서 여섯 ARM 제품을
새로 빌드하고 전체 호스트·고정 ARM 검사를 통과했습니다. 생략은 없습니다.
이는 [3625449의 첫 전체 ARM 실패](LDS_INLINE_PRODUCT_2026-10-02.md)를
성공으로 바꾼 기록이 아니라, 테스트 보강 후 별도 고정 사본에서 실행한 결과입니다.
새 설치 ZIP을 발행하거나 물리 CMU·센서·폰을 검사한 결과는 아닙니다.

## 고정 입력과 직접 실행 결과

두 깨끗한 detached 사본의 추적 파일 418개를 해당 커밋의 archive와
대조했습니다. 제품 빌드 입력 79개와 새 여섯 바이너리는 이전 `3625449`와
각각 같습니다. 차이는 채널 테스트 보강과 문서입니다. 이전 원본 LDS→AA
연결·ASSIST 복구 캡처는 계속 `3625449` 실행으로 표시하며 새 원본 실행으로
소급하지 않습니다.

도구체인은 `61ec0343de84f6fc7c46840056df1d600d44be8a`의 GCC 4.9.1,
ARMv7 Cortex-A9 NEON softfp입니다. 원본 firmware fixture와 실제 여섯 제품의
SHADOW 묶음을 지정했고, 호스트와 ARM을 순차 실행했습니다.

| 검사 | 결과 |
| --- | --- |
| 여섯 ARM 제품 새 빌드·묶음 생성 | 직접 종료 0 |
| 전체 `make test` | 직접 종료 0, 519.831초, Python 592개와 C/C++ 통과 |
| 전체 `tests/run_arm_all.sh` | 직접 종료 0, 448.158초, Python 118개와 C/C++ 통과 |

실제 DSO 사례는 POSITION 14, request 14, request-wire 1, endpoint 25,
provenance-context 7, association-context 17, session 29, bus 31,
assist 28, runtime-assist 9, context-pool 1, context-pool-association 12,
small-stack 2입니다. 선언된 목록, 개별 실행 파일·로그·종료 코드와 전체
runner의 suite 출력이 일치합니다. 원본 설치기의 84개 역시 선언·실행 목록과
각 저장 종료 코드를 대조했습니다. 설치기 사례는 원본 모듈을 사용하는 작성
fixture이며 실제 SM 기동과는 다릅니다.

Claude의 검토로 보강한 LDS 공유 채널은 호스트·ARM 전체 실행에 각각
17사례·1,162검사가 포함됐습니다. 별도 문맥 연결 10사례와 atfork 등록 실패,
작은 16/24 KiB 작성 스레드도 포함합니다. 이 스택 크기가 실제 AAPA의
최소 스택이나 잔여 여유라는 뜻은 아닙니다.

## 이전 실패와 후속 대조의 구분

`3625449` 첫 전체 ARM은 작성 센서 표본의 실제 수신 후 처리 지연이
251.299ms여서 250ms 제한을 넘었고 종료 134였습니다. 같은 binary의 단독
대조 성공과 별도로 실패를 보존했습니다. 이번 전체 실행에서는 같은
`bus_late_same` 사례를 입력·시간 제한·재시도 정책 변경 없이 통과했습니다.
과거 지연의 원인은 확정하지 않았으며 이번 성공으로 일반 스케줄링 지연이
없다고 보장하지 않습니다.

이번 실행 후 별도 판정기의 첫 시도는 source-linked 사례와 DSO 사례의
PASS 문구가 모두 전체 로그에 있을 것으로 잘못 예상했습니다. DSO별 문구는
개별 로그에 남는 runner 계약이므로 이 판정기 실패도 보존합니다. 제품이나
시험을 다시 실행해 바꾼 것이 아닙니다. 독립 대조는 실제 13개 DSO 기록과
190개 개별 로그를 읽고 통과를 확인했습니다.

## 독립 대조와 남은 범위

별도 읽기 검사에서 두 사본의 실제 418개 파일, 제품 입력 79개, 여섯 제품,
실제 시험 실행 파일과 결과 로그, 도구체인 기록 2,127개와 원본 runtime
모듈 29개를 다시 해시 대조했습니다. 전후 소스·도구·원본·패키지 목록은
같습니다. ARM 실행 시작·끝의 `ARM_TEST_INPUTS` 두 기록도 같은 여섯 해시와
`release_verified=true`를 보입니다. 작업 소유 채널·IPC·원본 경로 alias의
정리도 확인했습니다. 임시 검증 컨테이너 자체의 삭제는 후속 검증 종료 시
수행할 별도 작업입니다.

호스트 전체 로그 SHA-256은
`89cf0152a13d458ac53430da517987ecace8a5ae71c31411e8d2a413921a3568`,
ARM 전체 로그 SHA-256은
`db526220c1ee12fcde6daf056cfe7bedb7cf7ad5a5e1466f30d572d743ec0007`입니다.
AA 제품은 `9e248620c8f046586480f9e55b6f41819f75e12ca386cd99498d4a4dddcbce10`,
LDS 제품은 `2da6112779140af2760520e2143e56b2f4bcbdc18aa75a10f1abe997b6a4cff0`이며,
정적 TLS는 각각 196바이트·52바이트입니다.

새 LDS 제품의 첫 부분 SM VM은 설치·작성한 이전 boot 표식·guard 선택과
부분 그래프 시작까지 출력했지만, 240초 제한 전에 LDS 상태·설치 진단·
질의 결과를 내보내지 못했습니다. 종료 124를 제품 성공이나 LDS 고장으로
세지 않습니다. 단계별 즉시 수집을 보완한 후속 관측은 별도로 판정합니다.
전체 OEM 부팅, 물리 센서의 생산 시각·품질, 실제 공급부와 폰/지도 수용은
미검증입니다. live ASSIST는 비활성이고 v1.0은 미완료입니다.

이후 외부 `master`의 원본 로더 unwind 검사를 통합한 `9c8ef75`와
숫자 메뉴 안내를 정리한 `452291c`는 이 고정 실행에 포함하지 않았습니다.
제품 소스는 같지만 추가된 검사와 최종 설치 묶음은 별도로 검증합니다.
