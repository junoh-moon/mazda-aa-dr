## 단일 USB와 순정 셸 검사 범위

최종 ZIP을 풀어 순정 ARM BusyBox/libc에서 설치·일회성 기동 보호·collector·
숫자 메뉴·종료·회수·제거·재설치를 실행했습니다. 설치 USB 디렉터리를 guest
밖으로 옮기고 마운트 목록에서도 제거한 구간에서 실제 loader/guard/collector를
실행하여 설치된 내부 파일로 동작하는 것을 확인했습니다.

작성한 AA reset 기록과 새 boot/uptime 뒤에 메뉴2·재설치·재무장 없이 메뉴3을
실행했습니다. 현재 상태는 비활성이지만 이전 boot의 POSITION·motion·MODEL
행은 보존합니다. 완료 응답이 없거나 이전 boot의 응답만 있는 두 경우 모두
`status_exit=1`, `finish_exit=1`, `export_exit=0`이었습니다. 실행 중 fixture가
회수 archive의 원시 trace·collector 바이트/SHA와 설정·기동 파일 불변을
단언한 뒤 통과했습니다. 이 임시 guest/archive 자체를 장기 보존한 것은 아닙니다.

현재 종료 미확인을 이전 시험 실패나 정상 종료로 바꾸지 않습니다. 회수 성공도
계산 성공·누락 없는 종료의 증명이 아닙니다. 별도 계정 여섯 변형·계정 손실
복구 두 경우와 소유권 이전·활성 collector·경로 유형 회귀, 15초 종료 확인
실패와 USB 미마운트 처리도 통과했습니다. 마운트·입력 로그·boot 표식은 작성한
조건이며 실제 USB 교체·정상 전체 SM 기동·차량 재부팅은 실행하지 않았습니다.

JSON 행과 고정 ARM 관측 큐의 메모리 증가는 기능 기록에 명시했습니다.
큐 항목 수·기존 26 MiB 로그 회전 상한·저장 여유 정책은 유지하고,
계속 누적되는 새 로그를 추가하지 않았습니다. 실제 입력 주기와 다른 프로세스의
쓰기를 모르는 상태에서 보관 시간이나 파일시스템 고장 방지를 보장하지 않습니다.

## 선행 원본 실행과 실패 기록

원본 연결 대조는 선행 `f2ec7c2bed55080e9700b1509e016b6600f98cf6`의 새 제품에서

NMEA·초기화·즉시 WorkerScope는 작성한 조건입니다. 실제 runtime journal worker,
정상 전체 ServiceInit/SM이나 폰을 이 실행에서 검사하지 않았습니다.

최종 빌드 입력 63개와 다섯 산출물은 이 선행 제품과 모두 동일하며 두

것으로 세지 않습니다. 외부 `d3c6fa1` 및 `c62b313` VM 기록은 각각 다른 제품의
별도 결과이며 이번 endpoint 제품의 전체 실행 검증으로 합산하지 않습니다.

첫 최종 후보 `84d06da`는 host Python 421개·C/C++를 생략 없이 통과했지만,
ARM endpoint DSO 25개·Python 30개 뒤 worker fixture 컴파일에서 종료 1이었습니다.
GCC 4.9의 nested 빈 집합 초기화가 새 endpoint API 다섯 필드의 누락 경고를
발생시켰습니다. 같은 패턴의 네 fixture를 명시적 값 초기화로 고쳤습니다.
adapter 세 TU와 worker의 수정 전 실패, 수정 후 컴파일·링크와 worker/model
여섯 QEMU 실행을 확인한 뒤 위 새 pin의 전체 검사를 다시 통과했습니다.
제품 코드·경고 옵션·펌웨어 조건을 완화하지 않았습니다. 첫 ZIP과 실패 기록은
보존했으며 게시하지 않았습니다.

단일 USB 집중 검사의 상태 42개에는 collector가 없어 생략 1개가 있었습니다.
최종 host에서는 새 collector로 해당 검사를 실제 실행했으며 생략 0입니다.
과거 집중 검사나 첫 후보의 결과를 최종 전체 결과로 바꿔 쓰지 않습니다.
