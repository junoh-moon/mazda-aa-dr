# 원본 BLM 작업 큐와 LDS 위치 콜백 실행 — 2026-09-30

Codex가 격리 ARM VM에서 원본 **LDS AA용 API → BLM callback → 작업 큐 →
위치 worker → RequestSendPosition**을 실행했습니다. 기존 제품의 OBSERVE
후크에서 위치 입력을 확인했습니다. AA 세션을 초기화하지 않은 시험이므로 실제
send 관측은 0건입니다. 폰 수용·qualified provenance·ASSIST 완료가 아닙니다.

Claude의 별도 [비동기 요청 조사](LDS_ASYNC_2026-09-30.md), Codex의
[AA util·연결·지연 시험](LDS_CLIENT_LIFECYCLE_2026-09-30.md) 다음 단계입니다.
작업 중 최신 커밋을 확인했으며, Claude 기록의 범위 정정 `e5d87c1` 이후 새
조사 커밋은 확인되지 않았습니다. 이번 실행은 Codex가 직접 수행했습니다.
제품 소스·설치 ZIP·ASSIST 허용은 변경하지 않았습니다.

## 시험 방법

- NA 74.00.324A 원본 rootfs·Linux 3.0.35를 QEMU 7.2.22/Sabrelite에서
  실행했습니다. NIC·호스트 장치·호스트 공유 디렉터리가 없는 guest입니다.
  기존 kernel-entry machine ID 조정 뒤 userspace 전에 debugger를 분리했습니다.
  LDS 내부 객체를 debugger로 읽거나 LDS 코드·응답을 대체하지 않았습니다.
- 고정 GCC 4.9.1, ARMv7 softfp로 진단 프로그램 세 개를 빌드했습니다.
  r4는 r3의 동일 바이너리를 재사용했습니다. std::function은 실제 C++ 타입으로
  컴파일했으며 소유권 구조체나 shared_ptr control block을 수동으로 만들지 않았습니다.
  실행은 원본 libstdc++를 사용합니다. 이 fixture의 필요 버전은 GLIBCXX_3.4입니다.
- 원본 common-util을 먼저 NOW/GLOBAL 로드하고 BLM을 NOW/LOCAL 로드했습니다.
  원본 파일 해시·실제 load bias·함수 진입 바이트를 대조했습니다.
  함수 주소를 다른 펌웨어에 일반화하지 않습니다.
- 원본 singleton과 GetWorkerQueue를 사용했습니다. 큐 생성자는 이미 스레드를
  시작하므로 start를 중복 호출하지 않았습니다. 원본 startPop으로 소비를 켰습니다.
- r2부터는 생산 코드의 adapter·ARM veneer·install_v74를 그대로 링크했습니다.
  singleton/생산자 시작 전에 원본 해시·매핑·다음 send 검사를 통과한 OBSERVE
  후크를 설치했습니다. 관측 sink는 고정 배열에 값만 복사하며 기다리거나
  할당·로그 출력을 하지 않습니다. 원본 송신 함수를 성공 stub으로 바꾸지 않았습니다.

각 실행에서 소비 시작 전 4개 작업을 제출하고 200ms 관측 창 동안 callback 0개,
큐에 남은 캡처 4개를 확인했습니다. startPop 뒤 작업 스레드가 실행했습니다.
작업 순번·각 호출 횟수·동일한 opaque WorkersData 참조를 대조했으며 main과
작업 스레드가 다른 것도 확인했습니다. 이 200ms는 차량 지연 상한이 아닙니다.

r2의 합성 입력은 mode 0/2/3, 서로 다른 UTC와 부호·크기의 좌표·고도·방향·속도·
horizontal/vertical 값입니다. 원본 LdsGetPositionCb가 원본 생성자, shared_ptr,
PostWorker를 호출하게 했습니다. fixture가 doWork나 RequestSendPosition을 직접
호출한 결과가 아닙니다. 큐의 완료 표식과 join을 기다린 뒤 실제 후크 관측을
검사했고, 9개 필드가 합성 입력과 일치했습니다.

r3/r4의 API 요청은 한 건의 position 관측과 큐 완료 표식을 기다린 뒤 다음 건을
제출했습니다. 두 요청을 동시에 대기시킨 시험은 아닙니다. callback 주소는 실제
BLM 함수이며 작성한 callback wrapper로 대신하지 않았습니다. BLM은 userdata를
상위 위치 입력에 남기지 않으므로 이 관측만으로 제품의 요청 identity 연결을
구현했다고 보지 않습니다.

## 원본 큐 종료와 소유권

원본 stop의 성공 반환은 100이며, 종료 대기는 포함하지 않습니다. fixture는
작성한 callback이 자기 pthread_self를 기록하게 한 뒤 stop과 pthread_join을
차례로 호출했습니다. 원본 객체의 thread handle 필드를 추측해 읽지 않았습니다.
모든 실행에서 stop=100, join=0, 정상 프로세스 종료 0이었습니다.

캡처 생성/파괴 수는 **작성한 std::function payload**의 계수입니다. 원본 위치
worker의 모든 allocation/free, 메모리 누수 부재, 취소·경쟁·장기 큐 수명을
직접 관측한 수치가 아닙니다. 원본 worker의 IsAsync·생성·파괴 ABI 자체는
[앞선 객체 시험](REQUEST_PROVENANCE_2026-09-30.md)의 별도 근거입니다.

## 정상 응답과 제공자 종료의 차이

r4는 원본 dbus-monitor의 준비를 확인하고 첫 fixture를 실행했습니다. 버스에서
시험 connection 이름의 소유자를 식별하고, 그 sender의 GetPosition 두 건을
찾았습니다. 요청 serial 5/8에 대응하는 method return의 destination·reply_serial을
대조했으며, reply sender는 앞서 조회한 원본 LDS data 이름의 소유자와 같았습니다.
두 reply 본문은 원래 타입 순서의 9개 0값이었습니다. 별도 control 요청의
GetSelectedGPS_sync=0과 GetDRUnitStatus_sync=false/false/0도 관측했습니다.
이 조회들을 원자적인 수신기·측정 출처 증명으로 취급하지 않습니다.

첫 fixture 종료 뒤 직접 시작한 LDS launcher를 종료했습니다. 종료 137,
data/control 이름 소유자 소멸 신호, 별도 GetNameOwner의 NameHasNoOwner를
확인했습니다. 이후 새 fixture의 AA용 API도 각각 0을 반환했고, 원본 BLM 큐를
통과한 위치 관측은 다시 mode 0·9개 0값이었습니다.

**제공자 부재 case의 GetPosition wire 요청과 error는 dbus-monitor 기록에
나타나지 않았습니다.** 그 부재만으로 요청 미전송이나 특정 wire 오류를 단정하지
않습니다. 정상 case의 요청/reply 대응과 제공자 종료 뒤 상위 0값 전달은 확인했지만,
이번 monitor가 장애 경로의 모든 메시지를 포착했다고 주장하지 않습니다.
ServiceUnknown과 util의 NULL error 비교는 앞선 별도 API 시험의 근거입니다.

따라서 AA용 util을 거친 position 값만으로 정상 요청 완료를 판단할 수 없습니다.
실제 요청 출처의 제품 연결은 util보다 아래쪽의 오류·reply identity와 원본 정리
경계를 함께 다뤄야 합니다. 해당 연결은 여전히 **미구현**입니다.

## 판정 범위와 남은 작업

원본 callback→큐→doWork→RequestSendPosition과 기존 관측 후크의 실행 근거를
추가했습니다. AapProc::Init, LDS_UTIL_Init/Uninit, 정상 SM 전체 그래프,
AA 세션·구독·폰 연결은 실행하지 않았습니다. 초기화되지 않은 원본 manager의
송신 조건을 우회하지 않았으며, 각 실행의 send 관측은 실제로 0개입니다.

실제 AA send·반환·폰 수용, 요청별 provider/receiver/session 자격의 제품 연결,
물리 센서·생산 시각·보정 근거는 남아 있습니다. 현재 runtime의 provenance와
ASSIST 허용 상태를 바꾸지 않았습니다. [v1.0 조건](../docs/V1_READINESS_KO.md)을
완료 처리하지 않습니다.

결과 검사기는 입력/console 해시, 격리 설정, fixture 종료, 모든 작업 순번과
position 필드, 정상 bus 요청/reply 대응을 대조했습니다. 네 VM 실행은 guest
완료 뒤 바깥 runner 제한으로 종료 124, QEMU 종료 0, timed_out=true였습니다.
r1/r2/r3은 각각 120.032/120.007/120.008초, r4는 150.025초였습니다.
이 종료값과 시간은 통과 근거가 아니며 fixture의 검사와 정상 종료를 따로 확인했습니다.

정적 호출 검사 초안은 직접 BL에 PLT 전용 검사기를 적용해 실패했습니다.
직접 호출과 PLT 호출을 구분하여 원본 목표 주소 12개를 다시 확인했습니다.
제품 소스 변경이 없어 전체 make test·ARM 제품 회귀는 재실행하지 않았습니다.
이번 추가 검사는 위 세 ARM 빌드, 네 VM 실행과 결과 검사입니다.
이번 fixture의 새 독립 Claude/Codex 리뷰는 수행하지 않았습니다.
