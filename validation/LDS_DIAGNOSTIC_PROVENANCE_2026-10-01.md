# LDS 진단 API와 위치 출처의 연결 조사 — 2026-10-01

이 기록은 외부 `feat/session-observation`의 `ce12518` 정적 분석을
출처 그대로 보존한 것입니다. 원본 입력·API 형식을 root가 직접 대조한
범위는 별도 [통합 검토](LDS_DIAGNOSTIC_PROVENANCE_REVIEW_2026-10-01.md)를
따르십시오. 아래 원본 함수의 선택 명령어 분석은 외부 브랜치의 실행입니다.

원본 `GetUbloxDiag`를 추가로 조회하면 제품의 위치 응답에 수신기·센서 자격을
붙일 수 있는지 조사했습니다. 이 API는 별도 진단 캐시를 반환하며, 위치 응답과
같은 측정 묶음이라는 식별자를 제공하지 않습니다. 원본의 갱신 순서도 두 캐시의
일괄 갱신을 보장하지 않습니다. 이 조회로 live `provenance()`를 구현하지 않았으며
ASSIST는 계속 비활성입니다.

이번 작업은 `92dc20d4eb5a7846cb57e0cad5f6d0da7143e459`를 기준으로 한
**정적 분석**입니다. 제품 코드·설치 ZIP은 변경하지 않았습니다. 기존 원본
LDS·AA 실행 결과와 합성 자격을 사용한 선택 시험은 외부 브랜치의
`ASSIST_SELECTION_2026-10-01.md`를 따릅니다.

## 입력과 방법

제공된 NA 74.00.324A의 원본 파일을 보관된 실험용 initramfs에서 다시 추출했습니다.
이 이미지의 SHA-256은
`229a97ebd613cc71702359cdb22e65096a2b9caf9ae778724fa6b4c415758202`입니다.
진단용 기동 파일을 포함한 이미지이며, 이번에 읽은 LDS 파일은 보존된 원본입니다.
gzip CRC, newc 기록과 추출한 파일 11개의 크기·SHA-256을 확인했습니다.

| 조사한 주요 원본 | SHA-256 |
|---|---|
| `libjcilds-dbus.so` | `86fa094608e0c342ea759e522611d4c2d069006e2bb8909767f8835c164f18ce` |
| `libjcilds-ublox.so` | `aa1d4f5023c5f12093884e3b8a10bda07b234e4a36a793e333af010b522dbae5` |

내장 D-Bus introspection, 원본 함수 여덟 개의 명령어, ELF relocation을 대조했습니다.

무시된 로컬 `evidence/assist-binding-20261001-92dc20d/`에만 보관합니다.

## 확인한 계약

1. `GetPosition`의 출력은 기존 아홉 항목입니다. 첫 항목은 32비트 정수이며,
   UTC·좌표·고도·방향·속도·정확도 항목을 반환합니다. 수신기 세대나 원본 측정
   순번, 별도 진단 응답과 연결하는 snapshot 식별자는 없습니다.
2. `GetUbloxDiag`는 UTC, 속도·방향·자세·좌표, 버전·상태, 센서 상태와
   lever arm·위성 정보를 포함한 15개 출력 항목을 반환합니다. 이 메서드에도
   `GetPosition`의 특정 요청·snapshot과 연결하는 식별자는 없습니다.
3. 진단 getter는 자체 mutex 아래에서 진단 캐시 312바이트를 복사합니다.
   위치 getter와 위치 갱신은 별도의 mutex로 보호되는 48바이트 캐시를 사용합니다.
   각각의 복사가 잠금으로 보호된다는 사실은 두 응답이 같은 측정이라는 뜻이 아닙니다.
4. 조사한 u-blox 위치 메시지 경로는 먼저 위치 갱신 함수를 호출합니다.
   그 함수는 위치 잠금을 풀고 돌아가며, 이후 생산자가 진단 잠금을 얻어 UTC와
   좌표 등의 진단 필드를 갱신합니다. 두 갱신 사이를 함께 보호하는 잠금은
   이 경로에 없습니다. 위치 갱신 이후에도 이전 진단값을 읽을 수 있는 구조라는
   정적 근거이며, 그 경쟁 상황을 실행으로 재현한 결과는 아닙니다.
5. 센서 상태·위성·자세의 진단 필드는 서로 다른 수신 메시지 분기에서 갱신됩니다.
   따라서 진단 캐시를 한 번에 복사해도 모든 필드가 한 생산 시각의 측정이라고
   볼 수 없습니다. 필드별 생산 시각을 새로 얻은 것도 아닙니다.
6. 진단 응답의 안테나 상태에는 캐시 복사 이후의 marker 파일 검사도 사용됩니다.
   원본은 조건에 따라 `system()`으로 short/open 표식을 조회합니다. 반환값
   전체가 오직 복사 시점의 캐시만으로 구성된다고 가정해서는 안 됩니다.

최신 진단값, 같은 UTC 또는 같은 좌표를 근거로 과거 위치 응답에 수신기 자격을
붙이지 않습니다. `GetSelectedGPS_sync`의 전역 선택 상태 역시 특정 위치 응답의
출처 식별자가 아니라는 [이전 조사](REQUEST_PROVENANCE_2026-09-30.md)를 유지합니다.
u-blox 진단 API의 존재 자체로 대상 차량의 실제 수신기 종류를 확정하지 않습니다.

## 검증 범위와 남은 구현

비공개 확인 스크립트는 입력 해시, 두 API의 전체 출력 형식, 여덟 함수의 디코딩
재현, relocation과 선택한 갱신·복사·외부 호출 경계를 검사하여 종료 코드 0을
반환했습니다. 이는 정적 근거의 확인이며 제품 동작 시험 수에 합산하지 않습니다.
초기 스크립트가 표준 introspection 메서드의 중복과 위치 첫 항목의 형식을
잘못 가정하여 실패한 두 기록도 보존했습니다. 원본 형식과 대조하여 검사기를
수정했으며, 원본 펌웨어의 결함으로 분류하지 않았습니다.

이번에는 새 QEMU/LDS·AA 실행, `make test`, ARM 빌드·실행을 하지 않았습니다.
추적되는 변경이 검증 문서뿐이므로 제품 회귀를 다시 실행하지 않았으며,
[직전 제품 검증](VIP_ACCUMULATOR_2026-10-01.md)을 이번 실행 결과로 재기재하지 않습니다.
문서 상대 링크와 `git diff --check`를 확인했습니다.

제품에는 생산자→위치 snapshot→실제 요청·응답의 출처를 유지하는 연결이
**아직 구현되지 않았습니다.** 이 연결을 구현하려면 진단 polling과 별도로 원본
생산·snapshot 경계에서 식별자를 보존하고, 부분 갱신·무효화·재게시·늦은 응답을
구분해야 합니다. 그러한 연결도 물리 센서의 시간·품질, 실제 폰·앱 수용과
전원 복구의 증거를 대신하지 않습니다. [v1.0 완료 조건](../docs/V1_READINESS_KO.md)을
낮추거나 이번 조사로 상위 ASSIST 항목을 완료하지 않습니다.
