# 새 LDS 제품의 부분 SM 기동 관측 — 2026-10-02

`3625449ba1cd713c4b7ce13f778847acd86d8819`의 새 LDS 제품을 원본 커널·
rootfs의 부분 SM 그래프에서 관측했습니다. 두 번째 실행은 제품 설치 진단과
같은 LDS 프로세스의 반복 존재를 남겼지만, 정상 서비스 응답은 확인하지
못했습니다. 세 번째는 LDS 시작 전에 다른 원본 서비스 종료가 관측됐습니다.
세 실행 모두 호스트의 240초 제한으로 종료됐으며 전체 기동 통과가 아닙니다.

## 같은 제품과 명시적인 실행 경계

제품 LDS의 SHA-256은
`2da6112779140af2760520e2143e56b2f4bcbdc18aa75a10f1abe997b6a4cff0`,
정적 TLS는 52바이트입니다. AA는 196바이트 TLS의
`9e248620c8f046586480f9e55b6f41819f75e12ca386cd99498d4a4dddcbce10`입니다.
이 제품의 [별도 원본 reader→AA 실행](LDS_INLINE_PRODUCT_2026-10-02.md)과
[01cb939 전체 검사](LDS_INLINE_FULL_2026-10-02.md)는 각각의 실행 범위를
유지하며 여기의 SM 성공으로 합치지 않습니다.

QEMU 7.2.22 `sabrelite`, CPU 2개, 원본 커널·rootfs와 작성한 GPIO readback
모델을 사용했습니다. 원본 SM이 19개 서비스·21개 내부 의존성·2개 연결을
가진 부분 그래프를 실행합니다. 누락한 외부 의존성과 연결은 명시적으로
기록했고 원본 서비스 바이너리·재시도·reset 정책·시간 제한은 바꾸지 않았습니다.
진단 PID 1이며 전체 OEM 부팅, 실제 주변 장치·센서나 물리 복구를 재현한
것은 아닙니다. 설치기와 guard 선택은 실행했지만 이전 부팅 표식은 작성
입력입니다. 실제 Linux 재부팅이나 영구 저장장치의 지속성 증거가 아닙니다.

| 실행 | 실제 관측 | 판정 |
| --- | --- | --- |
| r1 | 설치·guard 선택·SM 시작 출력, LDS 상태 자료 미회수 | 미판정 |
| r2 | 설치 반환 진단, LDS 5개 스냅샷과 제품 매핑; 12개 D-Bus 조회는 주소 전달 오류 | 제한된 설치·프로세스 관측, 서비스 응답 미확인 |
| r3 | 조회 주소 전달 수정; 8개 조회는 실제 bus 오류 응답, LDS 시작 전 `settings` 종료와 watchdog 갱신 중단 | LDS 기동 미판정, 다른 서비스 종료 원인 미확정 |

각 wrapper는 종료 124입니다. 제한 종료 뒤 QEMU가 반환한 0을 성공으로
바꾸지 않습니다. 시간 제한 연장, CPU busy loop 또는 `nohlt`로 결과를
통과시키지 않았습니다.

## r2에서 확보한 사실과 조회 도구 결함

r1은 자료를 끝에서만 내보내다가 제한 시간 안에 LDS 근거를 남기지 못했습니다.
r2부터 별도 관측기가 단계별 명령·부분 출력·PID·starttime·실행 파일·
인자·매핑·stderr 목적지를 즉시 내보냅니다. 출력 범위와 횟수를 제한했지만
스냅샷의 원자성이나 console 쓰기의 최대 시간을 보장하지 않습니다.

r2의 LDS PID 2005/starttime 8672는 다섯 스냅샷에서 같았고 원본 서비스와
새 LDS DSO의 매핑, stderr의 SM 로그 연결을 확인했습니다. 스냅샷 시작부터
마지막 종료까지 guest uptime 94.46–147.53초입니다. 프로세스 상태에는
ptrace 정지 `t`도 있어 이 존재 관측을 정상 서비스 진행으로 세지 않습니다.
같은 PID의 재exec까지 배제한 연속 생존 증명도 아닙니다.

제품의 `state=installed`, `mode=4`, `install_attempted=1`, `install_code=0`
진단을 회수했습니다. 이 진단에는 PID가 없고 같은 로그 prefix/tail을
재출력하므로 여섯 출력 행을 여섯 설치로 세지 않습니다. 매핑과 진단만으로
현재 27개 hook 슬롯, 실제 dispatch나 공유 채널 채택을 증명하지 않습니다.

모든 D-Bus 조회는 서비스에 접속하기 전에 환경변수 누락으로 실패했습니다.
PC의 세 셸은 임시 환경대입을 함수에서 외부 명령으로 전달했지만, 원본
ARM BusyBox에서는 전달하지 않았습니다. 원본 셸을 QEMU-user로 실행해
작성한 변수 하나와 native Python 수신기를 대조한 결과는 직접 명령 0,
함수 앞 임시 대입 23, 격리 subshell의 명시적 export 0이었습니다. 실제
추출한 조회 wrapper에서도 r2 실패/r3 통과와 부모 환경 불변을 확인했습니다.
이는 셸 경계 검사이며 원본 D-Bus 서비스 응답 성공이 아닙니다.

## r3의 후속 중단과 남은 작업

r3는 조회 함수 내부를 subshell로 격리하고 bus 주소를 export하는 변경만
적용했습니다. 제품·관측 helper·커널·그래프·제한은 그대로입니다. 이전
autolaunch 오류는 사라졌고 여덟 조회는 실제 bus로부터 NameHasNoOwner
2개와 ServiceUnknown 6개를 받았습니다. 이 단계에 LDS는 시작되지 않았습니다.

마지막 스냅샷은 guest 89.04초에 끝났습니다. 89.142초에 원본 SM은
`settings` 종료와 reset 정책을 보고했고, 89.160초에는 watchdog 갱신을
중단한다고 출력했습니다. 그 뒤 새 관측 표식 없이 240.270초의 호스트
제한으로 끝났습니다. LDS PID·매핑·설치 진단과 늦은 응답은 없습니다.
이 기록만으로 settings 종료 이유, 새 제품과의 인과관계 또는 GPT/WFI
문제라고 확정하지 않습니다.
같은 제품의 r2도 guest 111.416초에 다른 원본 VBS의 reset 정책과
111.440초의 watchdog 갱신 중단을 출력했으나 관측은 147.53초까지
이어졌습니다. 따라서 watchdog 중단 문구만으로 r3의 정체를 설명하지도 않습니다.

원문·입력·이미지와 독립 readback을 보존하고 같은 저장 자료에서 비교합니다.
각 실행 뒤 작업 프로세스·UNIX socket·SysV IPC·임시 경로를 정리했습니다.
컨테이너 자체와 추가 검증 도구는 후속 작업 종료 시 별도 정리 대상입니다.
r2 console SHA-256은
`f43b29c3dc230efc38733dfc0fa31d2f8ac1b7af567e6bfe43f8386b08267870`,
r3는 `cdb1a782cd4280a1bce995945c9274eb84153a2b759f5f9b24286409606d3d14`입니다.

관측기 코드는 실제 Claude 리뷰와 독립 검토를 거쳤지만, 그 정적 검토가
순정 셸의 실행 차이를 미리 발견한 것은 아닙니다. 실제 실패·수정·재실행을
각각 남깁니다. 설치 후보 발행 판단, 전체 OEM 기동, 물리 센서의 생산 시각·
품질과 폰/지도 수용은 별도입니다. live ASSIST와 v1.0은 미완료입니다.
