# 원본 LDS 비동기 위치 요청의 실행 관측 — 2026-09-30

이 기록은 NA 74.00.324A의 원본 LDS 제공자와 원본 LDS data client·JCIDBUS를
격리 VM에서 실행해 비동기 `GetPosition` 요청의 수명 경계를 관찰한 결과입니다.
유효한 GPS, AA 세션·수신기 자격, 폰 수용이나 실차 검증이 아닙니다. 제품
소스, USB 설치물, 공개 ZIP은 바뀌지 않았으며 live `provenance()`는 계속
false, `allow_assist=false`입니다.

이전 시도는 fixture 컴파일과 이미지 생성 뒤 자동 보안 심사로 실행 단계가
중단되어 VM/GDB 관측이 없었습니다([요청 출처 기록](REQUEST_PROVENANCE_2026-09-30.md)의
남은 항목). 이번 실행은 사용자의 명시적 요청에 따라 같은 설계를 실행했습니다.

## 실행 구성

- 순정 Linux 3.0.35 커널, QEMU 7.2.22 Sabrelite, 기존 kernel-entry r1 조정,
  `nohlt enable_wait_mode=off`. `-nic none`, 호스트 장치·공유 디렉터리 없음.
- 진단 PID1이 원본 service/HMI 버스와 원본 launcher의 standalone LDS만
  시작했습니다. SM·VBS·AA·NNG, 제품 preload와 collector는 시작하지 않았습니다.
- 직접 작성한 fixture가 원본 `libjcicommon_util`, `libjcidbus`, LDS data
  client를 해시 확인 후 `RTLD_NOW`로 로드하고, 원본 API로 service bus 연결을
  만든 뒤 서로 다른 userdata로 `LDS_DATA_GetPosition`을 두 번 호출하고 나서
  원본 `JCIDBUS_dispatch`를 호출했습니다. 반환값을 바꾸거나 원본 함수를
  대체하지 않았습니다.
- 외부 GDB observer는 hardware breakpoint(Z1)만 사용하고 소프트웨어 breakpoint,
  대상 레지스터·메모리·코드 쓰기를 하지 않았습니다. 모든 정지에서 fixture
  main thread의 TLS와 일치하는지 확인했고, 모든 breakpoint 제거·detach 뒤
  fixture의 정상 종료를 요구했습니다.

## 결과 (r5)

| 경계 | 실제 관찰 |
| --- | --- |
| 연결 | `JCIDBUS_conn_connect` 반환 1. 아래 계약 정정에 따라 성공 |
| 요청 제출 | 두 `GetPosition` 모두 0 반환, 그때까지 callback 0건. 두 요청이 동시에 대기 |
| 원본 async send | 요청마다 서로 다른 method와 8바이트 context `{callback, userdata}`. notify는 data client의 reply 처리 함수, timeout -1 |
| reply 처리 진입 | 각 notify가 정확히 해당 요청의 method·context·connection으로 진입. 순서는 요청 1, 2 |
| reply identity | 두 reply 모두 method return(raw type 3), error 없음, sender `:1.1` |
| 제공자 대조 | 실행 전 `GetNameOwner(com.jci.lds.data)` 결과도 `:1.1`. LDS 프로세스는 하나였고 TracerPid 0 |
| 평탄화 callback | 정확한 userdata로 요청당 1회, error NULL, mode·UTC·좌표 등 아홉 값 모두 0 |
| 정상 정리 | callback 복귀 뒤 pending 정리가 같은 connection·method로 진입하고, 같은 method 해제 뒤 복귀 |
| 스레드 | 22개 정지 모두 dispatch를 호출한 fixture main thread |
| 원본 코드 대조 | 여섯 관측 지점의 코드가 실행 중 원본 파일과 일치했고 detach 전에도 동일 |

fixture는 내부 검사 31개를 통과하고 detach 뒤 종료 0으로 끝났으며, observer
정지 이벤트는 22개입니다. VM은 fixture 완료 뒤 `poweroff`했으며 경과 시간이나
QEMU 종료값을 판정 근거로 쓰지 않았습니다.

## 계약 정정과 실패 기록

- **r2 — connect 반환값 가정 오류.** 원래 fixture는 connect 성공을 0으로
  가정했습니다. 실제 반환은 1이었고, 원본 BLM `Dbus::Init` 호출부는 0일 때
  연결을 정리하고 오류로 끝나며 0이 아닐 때만 진행합니다. 라이브러리도 내부
  연결 결과를 그대로 반환합니다. 따라서 **connect는 0이 아닌 값이 성공**입니다.
  `LDS_DATA_GetPosition`과 `JCIDBUS_dispatch`는 원본 코드상 0이 성공이며 실행
  결과도 같았습니다. fixture만 수정해 새 이미지를 만들었습니다.
- **r3·r4 — 관측 도구의 메모리 읽기 시점.** 아직 실행되지 않은 원본 DSO
  페이지는 demand paging으로 debugger가 읽을 수 없었습니다. QEMU TCG는 명령
  fetch 전에 Z1 정지를 보고하므로 해당 함수의 첫 정지에서도 읽기가 실패했습니다.
  observer가 각 지점의 코드를 처음 읽을 수 있는 정지에서 대조하도록 바꾸고,
  detach 전 여섯 지점 모두의 대조를 필수로 유지했습니다.

실패한 세 시도의 console·metadata도 비공개로 보존했습니다. r2 observer는 fixture
실패 뒤에도 정지를 기다리다 240초 제한으로 끝났습니다.

## 설계에 주는 의미

- 원본 비동기 경로에서는 **요청 제출 → method/context → reply(sender) →
  userdata callback → pending/method 정리**가 실제 객체 identity로 이어집니다.
  두 요청의 값이 모두 0으로 같아도 method·context·userdata로 구분됐습니다.
- reply sender는 data client의 reply 처리 진입 시점, 정리 전의 reply 객체에서만
  얻을 수 있습니다. BLM이 받는 평탄화 callback에는 sender가 없습니다.
- callback은 `JCIDBUS_dispatch`를 호출한 스레드에서 실행됐습니다. 원본 BLM에서는
  ServiceRun 경로이며 AA 송신 스레드가 아니므로 send 시점 TLS만으로 요청을
  연결할 수 없다는 기존 정적 결론과 맞습니다.
- 정상 경로의 method는 callback 복귀 뒤 해제됩니다. 해제 뒤 주소 재사용에 대비해
  [요청 관측 자료구조](REQUEST_TRACE_2026-09-30.md)가 실제 파괴 경계에서만 슬롯을
  회수하는 계약과 일치합니다.

이 결과로 제품 hook 위치를 확정하지는 않습니다. 제품 연결에는 BLM callback 뒤의
worker 큐·position 송신까지의 identity, 취소·timeout·연결 끊김에서 callback 없이
정리되는 경로, 응답 순서 역전, 실제 AA 세션·수신기 자격이 추가로 필요합니다.

## 한계

- fixture는 data client의 `LDS_DATA_GetPosition`을 직접 호출했습니다. 기존
  비공개 정적 감사에 따르면 제품 BLM은 `libjcilds-util`의 AA용 요청 함수를
  거치며, 이 계층의 수신기 cache 조회와 추가 callback 평탄화는 이번 실행 범위에
  들어 있지 않습니다. 제품 요청 경로 전체를 실행한 결과로 해석하지 않습니다.
- LDS는 이번 VM에서도 GPS 없이 mode 0과 0 값만 반환했습니다. 유효 위치의
  생산 경로나 수신기 선택을 관찰하지 않았습니다.
- sender `:1.1`과 이전 owner 조회의 일치는 이 실행의 단일 LDS 프로세스에 대한
  대조입니다. 수신기·측정 출처 자격을 증명하지 않습니다.
- 명시적 disconnect/free, 취소, timeout, 재연결, 할당 실패는 호출하지 않았습니다.
- 응답 순서가 요청 순서와 같았던 것은 이번 두 요청의 관찰이며 보장이 아닙니다.
- Z1 정지는 타이밍을 바꿉니다. 지연·경합 특성의 측정으로 쓰지 않습니다.
- 원본 바이너리·전체 console·레지스터 기록은 공개하지 않습니다.
