# 응답 전 LDS 출처와 현재 AA callback 연결 — 2026-10-02

원본 LDS 송신의 잠금 경계에서 확보한 요청 식별자·아홉 위치 값·캐시 할당
출처를 현재 AA callback이 읽도록 제품 코드를 연결했습니다. 기존의
callback 이후 worker 결합과 달리, 이미 한 번 소비한 요청 Trace를 사용해
provenance 호출 전에 조회합니다. POSITION과 SEND는 같은 소유 사본을
보존하며 SEND에서 다시 조회하지 않습니다.

이 기록의 완료 범위는 아래 구성 요소의 집중 검사입니다. 새 여섯 제품의
전체 host/ARM 검사와 원본 LDS→원본 AA의 같은 실행 검증은 다음 단계입니다.
새 ZIP을 발행하지 않았습니다. 물리 센서 시각·품질·보정과 provider/receiver
자격은 구현 완료로 세지 않으며 `allow_assist=false`를 유지합니다.

## 구현

- 정확한 NA 74.00.324A 원본의 두 잠금 호출과 일곱 번째 모듈을 검증합니다.
  초기화되지 않은 잠금·실패·다른 호출 경로는 원본대로 전달합니다.
  27개 데이터 슬롯 설치는 원본 실행 코드 패치나 가짜 성공 반환을 하지 않습니다.
- LDS 시작 시 45,056바이트의 backing을 준비하고 경로를 unlink합니다.
  최대 64개 관측은 같은 메모리를 재사용합니다. 잠금 안의 게시에는 파일·socket
  I/O를 넣지 않았으며 원본 Path가 돌아온 뒤에만 읽기 전용 FD를 초당 최대
  한 번 제안합니다. 준비 실패는 기존 sideband·설치를 막지 않습니다.
- AA worker는 최대 두 control datagram을 처리하고 읽기 전용 map을 채택합니다.
  UID는 로컬 계정 확인일 뿐 LDS 실행 파일·센서의 자격 증명이 아닙니다.
  callback은 bounded atomic copy만 수행합니다. 교체·철회 중 빌린 map은
  reader가 끝나기 전 unmap하지 않습니다.
- 요청 키·아홉 값의 비트 일치, 중복·손실·창 종료와 이전 객체 재제안을
  구분합니다. 관측 시각과 map 생성 순서는 측정 시각·신선도가 아닙니다.
  worker 종료·중단·audit 실패·libc fork에서 새 조회를 철회합니다.
- 실패한 provenance callback은 부분적으로 쓴 자격 필드도 모두 지웁니다.
  JSON은 소유 출처를 두 행에 남기며 최대 길이 입력에 맞춰 worker의 행 버퍼를
  8,192바이트로 늘렸습니다. 기존 로그 파일 수·용량 제한은 유지합니다.

## 실제 집중 실행

| 범위 | 호스트 | 고정 GCC 4.9.1 ARM/QEMU |
| --- | ---: | ---: |
| LDS 원본 전달·잠금 게시 훅 | 50사례 | 50사례 |
| LDS cold 설치기 | 미지원 대상 거부 1사례 | 원본 모듈 84사례 |
| map/FD·수명·동시 접근 | 17사례·499검사 | 17사례·499검사 |
| 실제 Tap→FD 제안·동일 source_instance·fork·준비 실패 | 22사례 | 22사례 |
| 실제 runtime worker→Ledger→callback·철회·journal | 8사례 | 8사례 |

위 실행의 생략은 0개입니다. 설치기 외 행은 작성한 입력을 쓰는 소스 링크
시험이며 차량이나 원본 전체 부팅으로 세지 않습니다. 원본 설치기 역시 정상
ServiceInit·실제 제품 DSO 자동 기동을 대신하지 않습니다.
별도 adapter 문맥 17사례는 호스트·고정 ARM 모두 통과했으며,
`make test-adapter`도 호스트에서 통과했습니다.
새 실제 제품 DSO 문맥 suite는 전체 ARM runner에 등록했지만 이 집중 기록의
실행 결과로 세지 않습니다.

실제 runtime 검사는 채널 미채택 실패, 로그 필드 누락 실패, 최대 길이의
6,144바이트 버퍼 실패를 먼저 보존했습니다. 수정 후 측정된 POSITION
6,616바이트·SEND 6,822바이트(NUL 포함)를 새 버퍼에 기록하고 정확한 길이,
한 바이트 부족, 경계 밖 쓰기 방지와 입력 불변을 대조했습니다.

ARM FD 음성 대조에서는 QEMU가 수신 cmsg에 반환하지 않은 다섯 번째 FD가
열려 있는 것을 관측했습니다. 반환된 네 FD는 모두 닫힌 상태였습니다.
Linux 3.0의 `SCM_MAX_FD=253` 전체를 받을 고정 control 공간을 두고,
여전히 정확히 한 FD만 수락합니다. 253개 전송도 전부 거부·회수하여 FD 수가
증가하지 않는 것을 두 플랫폼에서 확인했습니다. 이 실패를 host 통과로
덮어쓰지 않았습니다.

별도 작성 scheduler는 이전 retire의 늦은 gate 닫기가 새 채택을 닫아,
같은 객체 재제안 후에도 조회가 복구되지 않는 반례를 재현했습니다.
철회의 단일 atomic epoch와 worker 전용 gate 변경으로 수정한 대조에서는
조회와 재제안이 복구됐습니다. 이는 host의 이전/현재 소스 대조이며 원본
펌웨어 실행이 아닙니다. 앞선 gate 소유권 invariant 검사와도 구분합니다.

고정 ARM의 정적 함수 frame 측정은 map prepare 5,376, publish 1,352,
drain 1,352, read 2,344바이트입니다. 전체 호출 사슬·원본 스레드 잔여 공간을
측정한 값이 아닙니다. [AA TLS와 작은 스택 위험](LDS_TLS_CRASH_2026-10-02.md)은
계속 별도 해결 대상으로 남습니다.

## 리뷰와 남은 검증

고정 `c09d7a9`의 첫 전체 제품 빌드는 GCC 4.9.1의 `-Os`에서 세 인자 CAS
overload의 failure memory order 오류 다섯 건으로 중단됐습니다. 이 실행은
전체 링크·bundle·host·ARM 전체 검사를 시작하지 못한 실패로 보존합니다.
성공/실패 memory order를 명시한 후속 수정은 실제 LDS·AA 제품 옵션의
object 컴파일과 host 17사례/499 assertion·ARM 17사례/499 assertion을
통과했습니다. 이것도 아직 전체 제품 검사를 대신하지 않습니다.

실제 사전 설치된 Claude CLI로 정적 반대 관점 리뷰, C++ 회귀 코드 작성,
AA 저장 구조 설계 비교를 수행했습니다. 생성된 코드는 검토·보완 후 직접
실행했습니다. 실패 provenance 필드의 잔류를 실제 assertion 실패로 확인하고
수정했습니다. 실패 식별자 보존이나 퇴역 객체 허용처럼 현재 계약과 충돌하는
제안은 채택하지 않았습니다. 리뷰 자체를 테스트 실행으로 세지 않습니다.

전체 제품 빌드·전체 검사·동일 제품의 원본 통합 실행, AA 스택 개선은 아직
이 기록으로 완료하지 않았습니다. live ASSIST 공급부, 물리 재부팅·센서·폰
수용도 남습니다. 새 도구 설치는 없었으며 이전에 추가한 격리 환경·GDB는
후속 검증에 사용 중입니다. 최종 제거 완료를 주장하지 않습니다.
