# 시험 후보의 기동 조건·GDB 관측 확인 — 2026-10-01

기존 [숫자 메뉴 후보 b185b99](KEYBOARD_TRIAL_2026-10-01.md)를 재빌드하지
않고, 실제 ARM DSO에 GDB를 연결했습니다. 요청 제출·worker 경계에서
중단점, 레지스터와 호출 스택을 확인한 뒤 기존 검사를 정상 종료했습니다.
별도 ARM 계산 시험에서는 MODEL 기준점 설정 성공과 계산 함수 진입을
확인했습니다. 차량·폰·순정 서비스 전체 기동을 실행한 결과는 아닙니다.

## 초기 기동 문제와 남은 조건

순정 BusyBox 1.19.2의 셸·awk 호환성, 없는 sha256sum 대신 정적 해시
도구 사용, USB noexec에 대응하는 실행 위치, UID 0 판정, 순정 경로 별칭,
읽기 전용 마운트 선택·복원과 한 번의 기동을 위한 arm 경로는
[기존 순정 셸 검증](USB_INSTALL_2026-09-29.md)과 최종 후보의 설치·상태·
종료·회수·제거 실행에서 검사했습니다. 마운트·센서와 파일시스템 조건을
작성한 chroot 검사이며 실제 flash remount나 전체 CMU 기동의 증명이 아닙니다.

SHADOW 계산에 필요한 기준점·세션·버스 조건이 충족되지 않을 때에도
수신한 원시 입력은 별도로 기록합니다. 이는 tap·수신 경로와 기록기가
정상 동작하는 범위의 계약입니다. 기동 자체가 실패하거나 공간·쓰기 오류가
있는 경우까지 원본을 영구 보존한다는 뜻은 아닙니다.

아직 다음 조건에서 시작·기록이 중단될 수 있습니다.

- 펌웨어·원본 바이너리·묶음 해시 불일치, 이전 영구 preload 또는 미완료 설치.
- 필요한 저장 공간 부족. 이 후보는 남은 로그 한도·payload와 8MiB 여유를
  설치 전에 확인하고 실제 가용량과 필요량을 출력합니다. 실차 여유량은 모릅니다.
- 실제 순정 서비스 순서·재시도·watchdog·AA 연결·센서 callback의 차이.
  주차 중 상태 메뉴에서 기동과 원시 입력 증가를 따로 확인해야 합니다.

따라서 알려진 초기 장애에 대한 실행 근거는 있지만, 실차에서 반드시
측정된다는 보장은 하지 않습니다. live ASSIST는 여전히 비활성이며
v1.0 완료 조건을 충족하지 않았습니다.

## 이번 직접 실행

기존 Docker 이미지에 GDB multiarch 13.1과 QEMU user 7.2.22를 임시
설치했습니다. 제공 펌웨어의 loader·libc 2.11.1과 공유 라이브러리를 사용했고,
설치 후 컨테이너의 외부 네트워크를 분리했습니다. QEMU의 GDB 포트는 같은
컨테이너 안에서만 사용했으며 호스트 포트를 공개하지 않았습니다.

| 실행 | 관측 | 결과 |
| --- | --- | --- |
| 실제 후보 DSO + 기존 `request-dso`의 `normal` 합성 호출기 | `mx5_request_submit`, `mx5_request_work_veneer`에서 실제 DSO 경로를 확인. 인자 레지스터·PC·호출 스택을 읽음 | debugger 없는 대조와 GDB 연결 실행 모두 기존 인자·반환·errno·scope 검사 통과, 종료 0 |
| 기존 ARM `live-pipeline-test` | `raw_shadow`→navigation→`mx5_dr_seed`의 실제 복귀값 0과 `mx5_dr_step` 진입 확인 | 대조·GDB 실행 모두 815 checks, 합성 송신 7회, 종료 0 |

두 번째 행은 계산 코드를 포함하는 별도 시험 실행 파일입니다. 첫 번째 행의
후보 DSO에서 실제 센서 계산을 관찰한 것으로 합치지 않습니다. 제품 파일,
입력·출력·자격 필드나 분기 조건을 debugger로 변경하지 않았습니다.
QEMU user는 호스트 커널을 사용하는 실행 방식이며 원본 CMU 커널 실행이 아닙니다.

실패한 시도도 비공개 근거에 보존했습니다. 먼저 선택한 `worker-session-test`는
시험용 동적 C++ 라이브러리의 `GLIBCXX_3.4.20`을 요구하여 순정 런타임에서
시작하지 못했습니다. 고정 SDK에서 실행하는 시험 파일이며 제품 DSO는
C++ 런타임을 정적으로 포함합니다. 이 실패를 제품의 순정 기동 실패나 성공으로
세지 않았고, 라이브러리를 바꿔 숨기지 않았습니다. 다음 계산 실행의 첫 GDB
`finish` 시도는 함수 복귀 대신 다음 seed 중단점에 도달했습니다. 최종 검사는
진입 때의 LR에 일회성 중단점을 두어 실제 복귀 지점과 r0를 확인했습니다.

## 조사 방법과 한계

PC에서 기존 ARM fixture를 `qemu-arm-static -g PORT -L STOCK ...`로
시작하고, 같은 격리 환경의 `gdb-multiarch`에서 원본 실행 파일·sysroot를
선택한 뒤 `target remote 127.0.0.1:PORT`로 연결했습니다. 공유 라이브러리가
로드된 후 함수 중단점을 걸고 `info registers`, `bt`, `info line *$pc`로
조사했습니다. 이번 실제 `.gdb` 명령 파일과 호출기는 아래 비공개 근거에 있습니다.
이는 개발 PC의 절차이며 차량에 입력할 새 명령이 아닙니다.

[QEMU 공식 GDB 안내](https://www.qemu.org/docs/master/system/gdb.html)는
system VM의 중단·레지스터·메모리 관측과 userspace 조사의 차이를 설명합니다.
이번 실행은 [user-mode GDB stub](https://www.qemu.org/docs/master/user/main.html)을
사용했습니다. [GDB 최적화 코드 안내](https://sourceware.org/gdb/current/onlinedocs/gdb.html/Optimized-Code.html)대로
최적화된 바이너리의 소스 대응에는 한계가 있습니다. 향후 자체 코드의 상세
변수 정보가 필요하면 같은 최적화 조건의 별도 `-g` 빌드와 실행 영역·주소
일치 확인이 필요하며, 아직 그 심볼 묶음을 구현·검증하지 않았습니다.

원본 서비스 userspace를 전체 VM 안에서 디버깅하는 작업과 차량에 호환
gdbserver를 붙이는 작업은 이번 범위가 아닙니다. 차량에서는 프로세스 정지가
서비스 감시·시간 제한에 영향을 줄 수 있으므로 주행 중 수행할 절차가 아닙니다.
중단점 실행은 정상 처리 지연의 측정 근거로도 사용하지 않습니다.
외부 master의 [LDS WFI 재실행](LDS_WFI_REPLAY_2026-10-01.md)은 전체 VM의
유휴 대기·타이머/IRQ 미해결 문제를 별도로 기록합니다. 이번 성공이 그
문제를 해결하거나 기본 QEMU의 정상 전체 기동을 입증한 것은 아닙니다.
외부 master `1385b5c`의 [후속 타이머 계측](LDS_TIMER_CAUSALITY_2026-10-01.md)은
GPT 비교값이 계산 시 이미 지난 경계를 좁혔지만 정상 전체 완주는 여전히 미검증입니다.
