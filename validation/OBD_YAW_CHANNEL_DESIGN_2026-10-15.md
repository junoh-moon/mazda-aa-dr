# OBD yaw 채널 2단계 설계와 오프라인 구현 (기록 전용, 2026-10-15)

대상: 소유자의 2019 MX-5 ND2, Mazda Connect NA 74.00.324A, beta.16의 휴대폰 IMU 채널(`PHONE IMU CHANNEL v1`). **차량·폰·OBD 어댑터·동글·DHU는 사용하지 않았습니다.** 모든 결과는 호스트 시험입니다. 이 기록은 차량 방문, 주행, 발행, 제품 입력 전환, 자격 ASSIST를 승인하지 않습니다.

표기: **FACT**(공개 문서·펌웨어·저장소 코드), **DATA**(저장소 기록의 수치·이번 시험 결과), **INFERENCE**(추론), **ASSUMPTION**(소유자가 승인한 작업 가정).

## 0. 요약과 불변식

- 휴대폰 앱이 OBD-II 어댑터(ELM327 v1.5 복제, JFIND JF327)에서 CAN 0x079를 단일 ID 수동 모니터로 받아, 기존 v1 DATA 프레임에 **한 CAN 프레임당 한 프레임**으로 실어 같은 RFCOMM 채널로 CMU에 보냅니다. 폰 자이로와 OBD yaw 중 **하나만** 보내며, OBD가 건강하지 않으면 즉시 자이로로 돌아갑니다.
- **CMU 수신기·collector·제품 코드는 바꾸지 않았습니다.** 와이어 형식(32바이트, CRC-32, 필드 배치)도 같습니다. 바뀐 것은 flags의 예약 비트 두 개에 뜻을 준 것(비트 4 `source_obd`, 비트 5 `obd_gap`)뿐이며, 1단계 CMU는 flags를 검사하지 않고 1초 묶음마다 OR로 기록합니다(FACT: `src/collector/phone_imu.h`의 `Aggregator::add`는 `b->fl |= d.flags`, `Decoder::next`는 flags를 보지 않음).
- **2단계는 기록 전용입니다.** DR은 계속 VIP를 거친 0x078을 씁니다. pimu 행은 runtime·worker가 읽지 않습니다. 네이버로 가는 어떤 값도 바뀌지 않습니다.
- 작업 가정(ASSUMPTION, 소유자 승인): 0x079(와 0x075)는 DLC에서 깨끗하게 들어옵니다. 근거는 `OBD_DLC_ND_EVIDENCE_2026-10-15`, `OBD_DLC_ND_EVIDENCE_FABLE_2026-10-15`이며 0x079를 DLC에서 직접 본 공개 보고는 아직 없습니다. 이 가정과 어댑터 처리율은 주차 10분 점검(`docs/OBD_YAW_CHECK_KO.md`)으로 확인합니다.

## 2. ELM327 초기화

순서와 이유(FACT: ELM327 데이터시트의 명령 정의; 선택 이유는 INFERENCE):

| 명령 | 기대 응답 | 이유 |
|---|---|---|
| (정지 문자) `X` | 프롬프트 또는 없음 | 앞 연결이 남긴 `ATMA`가 돌고 있으면 아무 문자나 모니터를 멈춥니다. 맨 CR은 보내지 않습니다: 프롬프트에서 맨 CR은 **직전 명령을 반복**(예: ATMA)합니다. |
| `ATZ` | 버전 줄(`ELM327 v1.5`) + 프롬프트 | 칩 리셋. 정지 문자가 입력 버퍼에 남는 칩이면 `XATZ`가 되어 `?`가 오므로 **한 번 다시** 보냅니다. |
| `ATE0` | `OK` | 에코 끔. 에코 줄은 파서가 TEXT로 버립니다. |
| `ATL0` | `OK` | 줄 끝 CR만. 파서는 LF도 받습니다. |
| `ATS0` | `OK`(실패해도 계속) | 공백 끔: 줄이 약 30 % 짧아져 UART·BT 부하가 줍니다. 파서가 공백 있는 형식도 읽으므로 **선택 사항**입니다. |
| `ATH1` | `OK`(필수) | 헤더(CAN ID) 표시. 없으면 어느 ID인지 모릅니다. |
| `ATSP6` | `OK`(필수) | ISO 15765-4 CAN 11비트 500 kbit/s 고정. 자동 탐색(`ATSP0`)은 **진단 요청을 송신**하므로 쓰지 않습니다. |
| `ATCAF0` | `OK`(필수) | CAN 자동 포맷 끔: ISO-TP 해석 없이 8바이트를 그대로 표시합니다. |
| `ATCRA 079` | `OK`(필수) | 수신 ID 필터: 0x079만 통과. |
| `ATMA` | 프레임 줄이 흐름(프롬프트 없음) | 모니터 시작. |

- **송신 안전(FACT, 코드):** 앱이 어댑터에 쓰는 것은 위 AT 명령과 정지 문자 `X`뿐입니다(`ElmController.SAFE_COMMAND`, 위반 시 예외). 16진 OBD 요청은 한 번도 쓰지 않으므로 어댑터가 차량 버스에 진단 프레임을 보내지 않습니다. 시험이 이를 바이트 단위로 확인합니다.
- **ACK(INFERENCE):** 정품 v1.4b 이상은 모니터 중 CAN 침묵(silent) 모드가 기본이지만, 소유자 복제칩은 `ATCSM`을 모릅니다. 침묵 모드가 아니라면 어댑터도 정상 프레임에 ACK 비트를 낼 수 있습니다. ACK는 여러 노드가 동시에 내는 정상 동작이라 버스에 해가 없다고 봅니다. 비트레이트를 `ATSP6`로 고정하므로 잘못된 속도의 오류 프레임 위험은 피합니다.
- **왜 단일 ID 필터인가(DATA·INFERENCE):** 공개 로그의 HS-CAN에서 주요 ID만 더해도 초당 수백 프레임이고(0x215·0x202·0x075·0x076 각 약 99 Hz, 0x078·0x079 각 약 50 Hz, 0x240·0x086 약 82 Hz 등) 전체는 1,000 fps를 넘을 수 있습니다. `ATS0`·`ATH1`에서 8바이트 프레임 한 줄은 `079` + 16자 + CR = 20바이트입니다. 필터 없는 `ATMA`는 1,000 fps × 20 B = 20 kB/s로, 복제 BT 어댑터의 흔한 내부 UART 38,400 baud(약 3.8 kB/s)를 몇 배 넘어 `BUFFER FULL`과 누락이 거의 확실합니다. `ATCRA 079`만 받으면 50 × 20 B = 1 kB/s(공백 켜짐이면 약 1.4 kB/s)로 여유가 큽니다. 0x075까지 받으려고 `ATCF`/`ATCM`으로 0x070~0x07F를 열면 0x075·0x076(각 99 Hz)과 0x078까지 들어와 약 300 fps(6 kB/s)가 되어 다시 한계를 넘습니다. 그래서 한 번에 한 ID입니다. 0x075(RCM, 0.01 deg/s, 영점 안정성 0x078의 약 27배)는 같은 코드에서 ID와 디코더만 바꾸면 되는 **다음 후보**로 남깁니다.

## 3. 모니터 출력 줄 해석 (`ElmLineParser`)

- CR 또는 LF가 줄 끝, `>`는 프롬프트입니다. NUL은 버리고 셉니다. 96자를 넘는 줄은 버리고 `MALFORMED`로 셉니다. 대소문자를 가리지 않습니다.
- CAN 줄: 공백을 지운 뒤 모두 16진이면 앞 3자리가 11비트 ID(0x7FF 이하), 나머지가 데이터입니다. 나머지 길이가 홀수이면 `ATD1`의 DLC 숫자로 보고 `1 + 2×DLC`와 맞을 때만 받습니다. 데이터는 최대 8바이트입니다. 세 형식(`07900112233…`, `079 00 11 …`, `079 8 00 11 …`)을 모두 읽습니다.
- 그 밖의 줄: `OK`, `?`, `BUFFER FULL`, `STOPPED`, 오류(`CAN ERROR`, `BUS ERROR`, `DATA ERROR`, `FB ERROR`, 프레임 뒤의 `<RX ERROR`/`<DATA ERROR`), 그 밖의 글(`NO DATA`, `SEARCHING...`, 버전, `LV RESET`, 에코)로 나눕니다. `<RX ERROR`가 붙은 프레임은 쓰지 않고 셉니다.
- 수신 시각: 줄을 끝낸 바이트 묶음을 받은 순간의 폰 `elapsedRealtimeNanos`입니다(수신 시각이며 생산 시각이 아닙니다).

## 4. 0x079 해독

```
raw12   = ((b3 & 3) << 10) | (b4 << 2) | (b5 >> 6)    DBC Motorola start bit 25, length 12
counter = b6 & 0x0F                                   (0x078 b6 >> 4와 같음)
qf      = b0 >> 6                                     횡가속도 필드의 품질 비트
yaw rad/s (시계 방향 +) = -(raw12 - 2047) * 0.000658615    약 26.5 카운트 / (deg/s)
```

| 주장 | 근거 | 신뢰 |
|---|---|---|
| 12비트 배치(바이트 3의 하위 2비트 ~ 바이트 5의 상위 2비트), 바이트 3 상위 6비트는 0 | DATA: 공개 로그 14,411프레임 전부 0x078과 같은 정수 격자 `round(2047.00190 + 1.52751423·n)`로 재현, 바이트 3 상위 6비트 관측값 {0} (`YAW_DECODE_2026-10-10`, 소유자 작업 트리; `VIP_0X079_GHIDRA_2026-10-12`가 인용) | 중상 |
| 단위·배율 = 0x078 계약(0.000658615 rad/s/카운트) | 같은 격자 공유 + 0x078과 상관 0.9999(`ND_CAN_LOG_2026-10-03`); 0x078 배율은 펌웨어 상수 26.5와 독립 추정 26.9·27.2·28.9(카운트/deg/s)가 1~9 % 안에서 일치. 제품 코드의 상수(`src/navigation/pipeline.cpp`, README) | 중(1~3 % 배율 오차 남음) |
| 부호: 카운트는 **좌회전에서 증가** → 시계 방향 + 는 `-(raw-2047)` | DATA: 우회전 양수 조향각과 상관 −0.971, 좌우 휠 속도 차와 −0.975(`ND_CAN_LOG_2026-10-03`, 0x078) | 높음 |
| 영점 2047 | **명목값만**. 공개 로그 정차 평균은 2047.50~2047.69(6구간, 변화폭 0.189카운트) | 영점은 앱에서 쓰지 않음(아래) |
| 계수기 = b6 하위 4비트, 프레임마다 1씩 증가 | 0x078 b6 상위 nibble과 14,411쌍 모두 일치는 DATA, **1씩 증가는 INFERENCE**(앱이 스스로 검증, 5절) | 중 |
| `0x000`/`0xFFF`는 무효 표지일 수 있음 | INFERENCE(공개 로그 범위 1737~2925, 0x078) | 낮음: 받지 않고 셀 뿐 |
| qf 값의 뜻 | 미확정(0x078은 모든 프레임에서 3) | 기록만, 거르지 않음 |

- **공개 DBC와의 관계(FACT·DATA):** berumiya DBC의 `YawRate_Corr : 31|16@0+ (0.223437,-114.4) deg/s`는 바이트 3~4만 읽어 하위 2비트를 버린 거친 값이며 부호는 좌회전 +(ISO)입니다. 배율은 저장소의 세 독립 추정과 약 1.5배 어긋납니다(`ND_CAN_LOG_2026-10-03`; 시험 벡터 `observed_max_2925_left_turn`: DBC +48.9 deg/s 대 우리 −33.1 deg/s, 비 1.48). 그래서 DBC 배율이 아니라 CMU의 0x078 계약을 씁니다. DBC 값은 시험에서 교차 확인용으로만 계산합니다.
- **0x078과의 관계(DATA·INFERENCE):** 두 신호는 같은 정수 격자를 쓰고, 그 정수 차이가 0~3단계에서 계단식으로 바뀝니다(13번 전환). 정차 평균의 전체 변화폭은 0x078 3.343카운트, 0x079 0.189카운트입니다. 즉 0x079는 0x078의 가변 영점 처리를 덜 받은 표현으로 보입니다(INFERENCE). 어느 쪽이 무보정 센서인지, 사용자 ND2에서도 그런지는 확정하지 않았습니다.
- **영점을 앱에서 학습하지 않는 이유:** 폰은 차속을 모르므로(단일 ID 필터라 0x202를 받지 않음) 정차를 판정할 수 없습니다. 프레임은 명목 영점 2047 기준 dθ를 싣고, 오프라인 분석이 CMU의 휠 속도로 정차를 찾아 `Σdθ − zero·Σwindow`로 영점을 뺍니다. 합이 선형이라 정보 손실이 없습니다.

## 5. 누락 자기 측정 (`ObdLossMeter`)

- **두 독립 척도:** (1) 수신율 대 공칭 50 Hz, (2) 4비트 계수기의 단계 k>1이면 k−1프레임 누락. 계수기 반복(단계 0)은 세기만 하고 버리지 않습니다.
- **모호한 공백:** 수신 간격이 8주기(160 ms)를 넘으면 BT 버퍼 지연과 계수기 한 바퀴(16프레임) 손실을 구분할 수 없어 `ambiguous`로만 셉니다. 그때 계수기 손실은 적게 셀 수 있으므로 **함의 생산율 검사**를 둡니다: (수신 간격 수 + 계수기 손실) / 경과 시간이 50 Hz ±10 %이고 10 s 이상 쟀을 때만 계수기 기반 손실률을 쓰고, 아니면 수신율 기반 손실률을 씁니다. 계수기가 프레임마다 1씩 오르지 않는 차라면 이 검사가 틀리므로 거짓 손실을 내지 않습니다(시험 있음).
- **판정(주차 점검용):** 프레임 0 → `NONE`; 45 fps 이상·손실 5 % 이하·500 ms 넘는 끊김 0 → `GOOD`; 30 fps 이상 → `MARGINAL`; 그 밖 → `BAD`. 기준은 소스 선택기의 건강 기준(2 s에 80프레임)과 같은 쪽에 두었습니다(선택 근거: 0x079 50 Hz에서 80 % 미만이면 1 s 묶음 dθ가 20 % 넘게 빠짐; INFERENCE).
- **보고 위치:**
  - 앱 진단 기록: 60 s마다 `obd_stats`(소스, 전환 수, 보낸/보류 창 수, 손실 측정 한 줄), 실행 끝마다 `obd_run_end`(이유, ELM 버전, foreign/BUFFER FULL/재시작/초기화/정지/오류 수, 디코드 거절 수: wrong_id/short/reserved_bits/sentinel, qf≠3 수).
  - CMU 기록(코드 변경 없음): 1초 묶음 `n` = 그 초에 받은 0x079 수, `Σwindow_ms` = 20 × n(덮은 생산 시간), flags OR의 비트 5 = 그 초에 손실 있음. 손실은 차량→어댑터→폰→CMU 전 구간이며, 폰→CMU 구간 손실은 기존 seq 공백으로 따로 보입니다.
  - 분석기: `tools/analyze_logs.py`의 `phone_imu.obd` 절(비트 4가 있는 묶음 수, 프레임 수, 초당 프레임, 덮개율, 손실 있는 묶음, 혼합 묶음). OBD 묶음이 없으면 이 키가 생기지 않아 기존 보고서는 그대로입니다.

## 6. v1 프레임에 싣는 방식 (와이어 변경 없음)

| 필드 | OBD 프레임의 값 |
|---|---|
| magic/version | `MX`, 1 (그대로) |
| flags | 비트 4 `source_obd`=1, 비트 5 `obd_gap`(직전에 손실 또는 모호한 공백), 비트 3 `frame_reset`(모니터 시작·재시작 뒤 첫 프레임, 소스 전환 뒤 첫 프레임); **비트 0~2는 항상 0** |
| seq | 세션의 같은 seq(소스와 무관하게 1씩) |
| t_end_ns | 그 줄의 폰 수신 시각(`elapsedRealtimeNanos`) |
| dtheta_urad | `-(raw12−2047) × 658.615 µrad/s × 0.020 s`, 반올림 오차를 다음 프레임으로 이월(누적 오차 ≤ 0.5 µrad; 3만 프레임 시험) |
| window_us | **20000 = 그 표본이 덮는 생산 주기**(수신 간격이 아님). 1단계 규격의 "t_end − t_start"와 뜻이 다르며, 비트 4가 이 뜻을 표시합니다. 이렇게 해야 CMU의 초당 Σwindow가 덮은 시간이 되어 손실이 바로 보입니다. |
| bias_urad_s | 0 (`bias_valid`=0) |

## 7. 재연결과 감시 (`ElmController`, `ObdLink`)

- OBD 링크는 **CMU 세션이 연결된 동안에만** 돕니다(자이로 센서와 같은 수명). 세션이 끝나면 어댑터를 놓아 다른 앱(Car Scanner)이 쓸 수 있습니다. 어댑터는 클라이언트를 하나만 받습니다: 다른 앱이 잡고 있으면 연결이 실패하고 백오프합니다.
- 연결: 표준 SPP UUID `00001101-0000-1000-8000-00805F9B34FB`, 보안 RFCOMM 뒤 실패하면 비보안 한 번(복제칩 다수가 비보안만 받음; INFERENCE). 실패 시 2 s에서 두 배씩 30 s까지 백오프하고, 프레임을 받은 실행 뒤에는 2 s로 돌아갑니다. CMU 쪽 회로 차단기와는 별개입니다(OBD 실패는 CMU 연결에 영향 없음).
- 감시 규칙(기본값):
  - 프레임이 흐르다가 1 s 동안 끊기면 `stall`: `X` → 프롬프트 → `ATMA`.
  - 모니터 중 프롬프트가 오면(보통 `BUFFER FULL` 뒤) `ATMA`를 다시 보냅니다.
  - 정지 문자가 남는 칩에서 `XATMA` → `?`이면 한 번 다시 보냅니다.
  - 10 s 안에 재시작이 6번이면 전체 초기화. 모니터 시작 뒤 10 s 동안 프레임이 하나도 없으면(시동 꺼짐, 필터·속도 문제) 전체 초기화. 프레임 없는 초기화가 3번 이어지면 연결을 닫고 백오프(어댑터를 붙잡고 무한히 명령을 보내지 않음).
  - 필수 명령이 거절(`?`)되거나 응답이 없으면 그 실행을 끝냅니다(`init ATCAF0: ?` 등이 기록에 남음).
- 모든 재시작에서 손실 측정의 사슬을 끊고(재시작 사이 시간을 손실로 세지 않음) 통합기를 리셋해 다음 프레임에 `frame_reset`을 붙입니다.

## 8. 소스 선택과 대체 (`SourceSelector`)

- 한 스트림에는 한 소스만 실립니다: CMU가 소스와 무관하게 초당 dθ를 더하기 때문입니다.
- OBD **건강** = 최근 2 s에 0x079가 80프레임 이상 + 가장 최근 프레임이 0.5 s 이내. 자이로→OBD는 건강이 **3 s 연속**일 때(이력 현상), OBD→자이로는 건강을 잃는 **즉시**입니다. 자이로 센서는 OBD 사용 중에도 계속 돌므로 대체가 즉시 됩니다. 전환 뒤 새 소스의 첫 창에 `frame_reset`을 붙입니다.
- 두 스레드(센서, OBD)의 제출 순서는 선택기 잠금 안에서 정해져 전환 직후 옛 소스 프레임이 섞이지 않습니다.
- 혼합 판정: 자이로 창은 대개 비트 2(`gravity_valid`)를 켜고 OBD 창은 비트 0~2를 끄므로, 한 1초 묶음의 flags OR에 비트 4와 2가 함께 있으면 그 초는 소스가 섞인 것입니다(분석기 `mixed_bins`). 중력 무효 자이로 창과 섞인 경우는 이 규칙으로 못 잡습니다(드묾).
- OBD 어댑터를 고르지 않으면 1단계와 바이트 단위로 같은 동작입니다(선택기가 항상 PHONE, 프레임에 비트 4·5 없음).
