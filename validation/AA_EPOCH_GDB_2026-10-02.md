# 같은 LDS 연결의 epoch 복구와 GDB 관측 — 2026-10-02

이 기록은 고정 `d66ec1ef2f8e7116e5735f518da3ac27004cb1f8` 제품을 사용한 비공개 원본 실행의 요약입니다.
제품이나 원본 코드를 수정하지 않았으며 새 릴리즈 검증으로 세지 않습니다.
실제 제품 association reader와 worker/channel을 사용했습니다.
작성 자격 대조는 실제 센서 자격을 의미하지 않습니다.

첫 association-epoch 실행은 마지막 GPS 전달을 기다리다가 실패했습니다.
당시 client 종료 코드는 91이었으며, 정상 reader Close는 없었습니다.
정상 JSON 370행과 절단된 마지막 497바이트를 구분해 보존했습니다.
마지막 control 응답 뒤 다음 위치 요청이 나타나지 않은 경계까지 확인했습니다.
모니터에 응답이 있다는 사실만으로 로컬 pending 소비를 단정하지 않았습니다.

그 경계를 보기 위해 final wait에도 기존 POSITION 진행 watcher를 연결했습니다.
원래 phase 시간, 전체 제한 시간, 단 한 번의 capture 제한을 유지했습니다.
정확한 현재 ELF와 일치하는 경우에만 고정 길이 메모리를 읽도록 준비했습니다.
주소나 프레임이 맞지 않으면 명시적인 미결론을 남기도록 했습니다.
함수 호출, breakpoint, 원본 메모리 쓰기는 추가하지 않았습니다.
작성 process/clock/MI/memory 대조 41개는 모두 통과했고 skip은 없었습니다.
이 작성 대조를 실제 target 메모리 판독 성공으로 세지 않았습니다.

승인된 후속 원본 진단은 한 번 실행해 종료 코드 0으로 끝났습니다.
실행 시간은 32.712초였고 host timeout은 없었습니다.
GDB는 실제 연결됐으며 초기 continue를 수행했습니다.
이후 정체가 재현되지 않아 stalled capture는 0회였습니다.
따라서 새 pending 식별기는 호출되지 않았습니다.
unsupported target snapshot이 얻어진 것도 아닙니다.
현재 library range, 프레임과 pending 객체의 실경로 판독은 미검증입니다.

이번에는 완전한 JSONL 339행과 정상 capture 종료가 남았습니다.
원시 POSITION과 LOCATION 송신은 21쌍이었습니다.
초기 unavailable 3쌍과 실제 Owned가 연결된 18쌍을 구분했습니다.
시작 이후 POSITION 18개는 순서를 유지해 작성 source에 전달됐습니다.
원본 수치 189개와 실제 송신의 대응을 저장 자료에서 확인했습니다.
DR 적용은 6회였으며 그중 복구 이후가 3회였습니다.
BEGIN 2회, 입력 생산·소비 505개와 제품 발행 131회를 확인했습니다.
발행 상태를 읽은 411개 표본과 실제 발행 횟수를 구분했습니다.

음성 callback에서는 실제 Owned와 요청 연결을 유지했습니다.
작성 source epoch만 후보와 다르게 해 EPOCH_MISMATCH를 확인했습니다.
이때 원본 48바이트를 보내고 동일 POSITION을 뒤이어 소비했습니다.
이후 fault/철회와 마지막 GPS 원본 복귀를 확인했습니다.
client와 reader server는 정상 종료했고 원본 Close도 반환했습니다.

고정 fixture 컴파일 결과는 준비한 client/server와 바이트가 같았습니다.
선택 입력 174개, 원본 LDS 9모듈, 고정 소스 432개를 전후 대조했습니다.
제품 빌드 입력 81개와 여섯 제품도 변하지 않았습니다.
소유 프로세스·채널·IPC·별칭을 정리했으며 추가 원본 실행은 하지 않았습니다.
첫 실패와 후속 성공, 판독기의 초기 경로·종료행 가정 오류를 모두 보존했습니다.

GDB 연결과 달라진 스케줄의 시간 영향을 배제할 수 없습니다.
이번 성공은 기존 정체의 원인을 찾거나 제품을 고쳤다는 증거가 아닙니다.
부분 초기화와 작성 자격을 사용했으며 full ServiceInit은 검증하지 않았습니다.
물리 측정 시각·센서 품질·휴대폰·앱 수용·실차 동작과 live ASSIST는 미검증입니다.
