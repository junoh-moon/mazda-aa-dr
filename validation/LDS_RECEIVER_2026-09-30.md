# 원본 LDS 수신기 선택 대기의 추적 — 2026-09-30

NA 74.00.324A 원본 LDS의 USB 목록 응답, 실제 callback, 이벤트와 재시도
타이머를 격리 VM에서 확인했습니다. **유효한 GPS 응답과 원본 직렬 입력을
사용한 제품 MODEL은 아직 검증하지 못했습니다.** 다섯 실행의 위치 80건은
모두 mode 0·READ_NOT_READY=5입니다. 차량·폰·동글은 사용하지 않았습니다.

## 고정 조건

시작 소스는 `b4ea8f2f19a4bd2c09c22adf0a897c5f796bd2c3`이고 r11의 helper는
통합 커밋 `1ccedbf`에서 실행했습니다. 아래 수신기 진단에는 제품 preload나
AA caller를 실행하지 않았습니다. 조사 중 발견한 외부 `cb65fd5`를 합친
[제품 통합 검사](BUS_CLOCK_MERGE_2026-09-30.md)는 이 다섯 실행과 구분합니다.

[앞선 r6](LDS_INPUT_STARTUP_2026-09-30.md)의 원본 커널·LDS·SM·SYSTEM·USB
관리자와 9개 서비스 구성을 유지했습니다. 원본 LDS XML은 보존하고 별도
진단 XML에서 primary port만 작성 PTY로 지정했습니다. 하드웨어 제어와
StartupMode 설정은 원래 값입니다. feeder는 합성 GSA/GGA/RMC의 유효·무효·
재유효 문장을 공급합니다. 문장 생성은 원본 파서의 소비 증거가 아닙니다.

진단 PID1과 기존 CMU entry의 machine ID 인자 조정을 사용했습니다.
커널·OEM 바이트는 바꾸지 않았고, 네트워크·호스트 장치·공유 폴더를
VM에 연결하지 않았습니다. GPIO 값·수신기 선택·SYSTEM 상태·위치 응답을
성공값으로 대신하지 않았습니다.

## 직접 실행 결과

| 실행 | 추가한 관측 | 위치 / feeder |
| --- | --- | --- |
| r7 | 원본 dbus-monitor, libusbx 로그, USB 파일시스템 조회 | 16건 mode 0, 입력 241묶음, feeder 종료 0 |
| r8 | LDS에만 원본 함수 전달을 보존하는 진단 preload | 16건 mode 0, 입력 245묶음, feeder 종료 0 |
| r9 | 빈 `/dev/bus/usb` 디렉터리와 GPIO 읽기 | 16건 mode 0, 입력 248묶음, feeder 종료 0 |
| r10 | 원본 USB 관리자에 strace 부착 | 16건 mode 0, 입력 246묶음, feeder 종료 0 |
| r11 | USB 초기화 전 정지·strace 부착·재개 | 16건 mode 0, 입력 237묶음, feeder 종료 0 |

모든 실행에서 실제 USB 목록 요청과 해당 serial의 응답을 연결했습니다.
응답은 빈 장치 목록과 정수 결과 1입니다. libusbx의 usbfs 부재 오류가
있어도 이 응답은 전달됐습니다. r9의 빈 디렉터리 생성으로 usbfs 오류가
사라지지 않았으므로 디렉터리 부재만을 원인으로 확정하지 않습니다.

r8의 진단 preload는 원본 USB callback, `lds_PostEvent`, 타이머와 수신기
대기 함수를 호출 전후에 기록합니다. 인자·callback 포인터를 바꾸지 않고
원본을 한 번 호출하며, 결과·errno를 보존합니다. VM 인자·환경 표식이
없으면 실행을 거부하며 제품에는 포함하지 않습니다. 원본 함수 조회에
실패하면 진단을 종료합니다. 이번 실행의 조회 실패 기록은 0입니다.

수집한 r8 snapshot에는 USB callback 진입·복귀 각 1회, 수신기 대기 함수
진입·복귀 각 364회가 있습니다. 재시도 이벤트 17의 등록은 365회 모두
원본 결과 100이며, 타이머 Restart 결과 2와 이어지는 Start 결과 1도 각각
365회입니다. 이는 수집 시점의 snapshot이고 VM 전체 수명 동안의 총계는
아닙니다. USB callback이나 재시도 타이머 자체가 전혀 실행되지 않는다는
가설은 이 실행과 맞지 않습니다.

원본 수신기 대기 코드는 USB 전원 GPIO 조건이 충족되지 않으면 대기
횟수를 되돌립니다. r9에서는 `DO_OTG_PWR`와 `DO_HOST1_PWR`를 각각 16회
읽었고 모두 읽기 성공·값 0이었습니다. 원본 USB 관리자의 전원 켜기 로그와
이 값의 차이를 후속 r11에서 조사했습니다. 누락된 thermal 경로와 SYSTEM의
standby 전환 시도도 남아 있으며, 단일 원인으로 확정하지 않습니다.

r10은 USB 관리자의 12개 스레드에 실제로 부착하고 20초 뒤 정상 분리했지만,
관측 구간에서 최초 전원 파일 open/write를 포착하지 못했습니다. 기록된
다른 fd의 `1` 읽기를 전원 GPIO 값으로 간주하지 않습니다. 전원 쓰기 실패와
가상 GPIO의 읽기 동작 문제를 이 실행만으로 구별하지 못했습니다.

r11은 USB 서비스 전용 진단 preload가 초기화 전에 SIGSTOP을 발생시키고,
원본 strace를 붙인 뒤 계속 실행하도록 했습니다. 환경 표식은 자식 exec에도
상속되어 두 자식의 정지·재개가 추가로 보였습니다. 기동 시각을 바꾼 진단이며
평상시 기동 시간의 근거가 아닙니다. syscall 인자·결과·GPIO 값은 대체하지
않았고 제품에는 포함하지 않습니다.

이번에는 두 GPIO 각각의 원본 open→read `0`→close→open→write `1`→close를
포착했습니다. write는 모두 1바이트 성공, close는 0이었습니다. 이후 각
16회 읽기는 계속 성공·값 0이었습니다. fd 7의 `1` 읽기도 `ACC_Sense`로
식별했으므로 전원 GPIO 읽기로 세지 않습니다. 최초 USB 전원 write syscall
실패라는 설명은 이 실행과 맞지 않습니다. 모든 다른 writer와 커널 레지스터
경로까지 추적한 것은 아니므로 가상 GPIO 하나만을 원인으로 확정하지 않습니다.

설치한 QEMU는 7.2.22입니다. [같은 버전의 upstream GPIO 구현](https://gitlab.com/qemu-project/qemu/-/raw/v7.2.22/hw/gpio/imx_gpio.c)은
PSR 읽기에서 출력 방향 비트를 가립니다. 원본 드라이버가 이 경로를 읽는지와
배포 패키지 구현까지 대조할 필요가 있어, 현재는 VM 읽기 경로에 대한 가설입니다.
실제 GPIO 레지스터 근거를 확인하기 전에 성공값을 강제하지 않았습니다.
