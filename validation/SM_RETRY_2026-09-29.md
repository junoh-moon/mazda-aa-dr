# 실제 OEM SM의 재시작·지연 종료 관찰

NA 74.00.324A의 원본 Linux 3.0.35, SM, `sm_svclauncher`, AA BLM과 기존
touch 라이브러리를 격리된 QEMU에서 실행했습니다. 진단 PID 1과 RAM rootfs를
사용했으며 `nohlt enable_wait_mode=off`를 전달했습니다. 호스트 네트워크·장치·
공유 디렉터리를 VM에 연결하지 않았습니다. 전체 차량 기동이나 휴대폰 수용
검증이 아닙니다.

설치한 묶음은 `build/final-usb-r2`이며 기록된 source commit은
`e1f7ea2624317ba630c4a0077e561ab8a998d587`입니다. 후속 항법 수정본의 검증으로
소급하지 않습니다. 원본 함수 응답을 성공 stub으로 바꾸거나 가짜 서비스 PID
파일을 만들지 않았습니다. ASSIST는 계속 차단했습니다.

## 결과와 제외한 실험

| 실행 | 실제 결과 | 해석 범위 |
| --- | --- | --- |
| full-r1 | 원본 전체 서비스 그래프에서 실제 `smctl --launch`로 AA를 시작했습니다. 같은 SM PID 779 아래 AA PID 1225 → 명시적 restart 후 2020 → SIGKILL 및 명시적 launch 후 2899를 확인했습니다. 각 프로세스에 우리 preload와 기존 touch가 다시 적용됐습니다. | GUI/Opera 실패로 SM이 이미 watchdog 중단 상태였습니다. 종료 뒤 8초만 관찰했으므로 일반 자동 재시도 정책을 확정하지 않습니다. 200초 제한으로 말단 로그 출력도 잘렸습니다. |
| reduced-r2 | AA 하나만 남긴 진단 SM에서 초기 후크 설치와 RUNNING을 확인했습니다. restart의 stop 뒤 SM 자체가 종료됐습니다. 시작 콜백은 `109:In Progress`였지만 `smctl` 종료 코드는 0이었습니다. | 마지막 서비스 종료가 만든 진단 구성의 영향입니다. 후속 SIGKILL 대상이 없었으므로 crash 실험에서 제외했습니다. 현재 harness는 이 경우 명시적으로 SKIP합니다. |
| reduced-r3 | 원본 settings와 AA 두 서비스를 유지하여 마지막 서비스 종료 영향을 피했습니다. 같은 SM PID 802 아래 AA PID 814 → 명시적 restart 후 1133이 모두 RUNNING이었습니다. 두 세대 모두 `install=ok`, `hook_installed=true`, `runtime_mode=1`을 확인했습니다. | 나머지 서비스와 settings의 의존성 1개, AA의 의존성 7개를 생략한 진단 설정입니다. 대상 서비스의 retry/reset/timeouts/계정/launcher 속성과 preload 순서는 보존했습니다. 제품 설정에는 적용하지 않았습니다. |

reduced-r3에서 guest uptime 75.95초에 AA PID 1133에 외부 SIGKILL을 보냈습니다.
이는 지연된 자식 종료의 주입이며 라이브러리 자체가 크래시했다는 증거가 아닙니다.
78.477초에 순정 SM은 AA의 `reset_board=yes` 종료를 감지하고, 보고서 생성 뒤
watchdog ping을 중단하여 재부팅을 유도한다고 기록했습니다.

그 뒤 명시적 시작 요청 없이 166.41초까지 관찰했습니다. SIGKILL 뒤 약 90초이며,
네 관찰 시점에 새 AA 프로세스는 없었습니다. 마지막 SM 조회는 AA STOPPED,
settings RUNNING이었고 SM과 settings PID가 유지됐습니다. 최초 상태 조회는
timeout으로 끝났으므로 성공 조회로 세지 않았습니다. 물리 watchdog에 의한 실제
보드 재부팅은 이 VM에서 확인하지 못했습니다.

자동 동작 관찰을 마친 다음에만 `smctl --launch`를 보냈습니다. 같은 SM 아래 새
AA PID 1714가 생성되어 RUNNING과 새 `install=ok`/후크 health를 확인했습니다.
기존 touch와 우리 preload가 다시 매핑됐습니다. 전 과정에서 guard의 `arm`은
없고 `consumed`·`last-boot`는 유지됐으며, 두 번째 guard select는 2로 거부됐습니다.

## 계약 판정

현재 구현은 **한 번 선택된 SM 부팅의 시험 권한**이며, AA 프로세스를 단 한 번만
실행하는 권한이 아닙니다. 같은 SM 안의 명시적 관리자 restart/launch는 저장된
trial 환경을 다시 적용합니다. 이 동작만으로 기존 one-boot 계약 위반이나 자동
crash loop를 확정할 수 없습니다.

이번 지연 SIGKILL 경로에서는 순정 SM의 보드 재부팅 정책을 관찰했습니다.
다음 guard 경유 기동이 baseline을 고르는 구현과, 물리 재부팅·내구성이 실제로
성공하는지는 구분합니다. 생성자 실패, 다른 signal, hang, 파일시스템 실패,
실제 차량의 watchdog·전원 주기까지 이 결과로 일반화하지 않습니다. AA 위치
송신, 터치 입력과 휴대폰 지도 동작도 이 실험의 판정 대상이 아닙니다.

## 후속 설계에 사용할 원본 근거

원본 `<connect service_launcher_path="/jci/sm/sm_svclauncher">`는 전역 launcher
경로입니다. 원본 `SM_so_spawn`은 이 설정을 읽어 `posix_spawn`의 실행 경로로
전달하며, 서비스별 환경도 시작 때마다 구성합니다. 따라서 진단 config에서 이
경로를 정적 pre-exec helper로 바꾸는 실험은 가능합니다. 서비스별 plugin path를
다른 ABI의 wrapper로 바꾸는 방식은 아닙니다.

helper가 별도 자식을 만들지 않고 원본 launcher로 `execve`한다면 PID를 유지하는
후보가 됩니다. 원본 argv, 환경, 열린 FD, 자격, signal 상태와 IPC의 실제 보존은
추가 실행 검증이 필요합니다. 전역 설정이므로 AA/VBS 외 모든 서비스의 원본
실행도 보존해야 합니다. 이 helper는 구현하지 않았으며, one-boot 계약을 임의로
one-process 계약으로 바꾸는 제품 수정도 하지 않았습니다.

## 재현과 검사

`oem_system_emulation.py run --phase retry`는 원본 전체 설정을 사용합니다.
`--kernel-arg mx5retry=reduced`는 위의 settings+AA 진단 설정을 사용합니다.
각 snapshot은 실제 PID·preload·관련 mappings·runtime boot/health·guard 표식을
기록하고, 종료 뒤 자동 동작 관찰이 끝난 다음에 명시적 launch를 수행합니다.
`smctl`의 종료 코드만으로 성공을 판정하지 않습니다.

`python3 tests/packaging/test_oem_retry_probe.py`의 4개 authored-fixture 검사를
통과했습니다. 서비스 속성·preload·connect 보존, 누락/중복 대상 거부, 의존성 수
변경 거부와 shell 문법을 검사했습니다. 원본 XML의 축소 결과도 별도로 파싱해
비교했고, 실제 ARM BusyBox의 결과는 위 OEM 실행에 포함됩니다.

원본 전체 로그와 실행 JSON은 비공개 `evidence/oem-retry-full-r1.*`,
`evidence/oem-retry-reduced-r2.*`, `evidence/oem-retry-reduced-r3.*`에 있습니다.
각 initramfs의 입력 hash와 진단 코드 hash는 build sidecar에 있습니다. 원본 OEM
파일·memory map·전체 로그를 공개 산출물에 포함하지 않습니다. 실행 제한에 도달한
QEMU 종료와 inspection shell 진입은 성공 판정이 아닙니다.

## 2026-09-30 후속 진단 필터 수정

위의 당시 4개 검사 결과는 그대로 보존합니다. 후속 리뷰에서 reduced XML
필터가 주석 속 서비스를 되살리거나 손상된 wrapper를 성공으로 처리하는
문제를 재현해 수정했습니다. 새 host/순정 ARM BusyBox 검사와 입력·출력
해시는 [후속 OEM/필터 기록](OEM_LOCATION_2026-09-30.md)을 따릅니다.
과거 세 initrd의 원본 XML에는 해당 손상 패턴이 없었으며 정상 출력도
일치했습니다. 이 수정이 기존 원본 SM 실행을 다시 수행했다는 뜻은 아닙니다.
