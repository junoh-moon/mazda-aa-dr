## 관측한 적용과 복구

- 원본 요청/응답의 여섯 식별자로 위치/송신 18쌍을 연결하고 원시 값
  162개를 별도로 대조했습니다.
- 실제 제품은 작성 입력 511개를 소비했고, 서로 다른 계산 시점 70개에
  걸친 후보 표본 131개를 기록했습니다. 이 횟수를 물리 센서 표본이나
  실제 위치 정확도로 해석하지 않습니다.
- 최초 단절 구간의 DR 대체 3건 뒤 readiness 철회로 대체가 중단됐습니다.
  readiness만 복원했을 때는 재개하지 않고, 새 GPS·BEGIN 뒤 3건을
  다시 대체했습니다. BEGIN은 합계 2건입니다.
- 유효 후보가 있던 16번째 callback의 작성 출처 거부는
  `BAD_PROVENANCE`와 원본 48바이트 송신을 남겼습니다. 그 false 출처의
  POSITION을 송신 뒤 15.924ms에 값 변경 없이 worker에 넘겼고,
  실제 소비가 INPUT_FAULT로 이어졌습니다.
- 마지막 GPS callback 17·18은 원본 위치를 그대로 송신했습니다.
  원본 Close 반환과 reader fd 종료, 실제 worker 종료 기록도 확인했습니다.

기존 수치 판독기와 별도 저장 캡처 판독이 모두 통과했습니다. 원본
송신의 로컬 반환은 폰이나 지도 앱이 위치를 수용했다는 증거가 아닙니다.

## 독립 판독·최초 실패·정리

준비 스크립트는 처음에 과거 판독기가 남긴 `__pycache__` 때문에 디렉터리
집합 검사에서 종료 1이었습니다. 복사·컴파일 전 실패를 보존하고 정규
입력 14개와 별도 디렉터리를 구분한 뒤 진행했습니다.

독립 판독기의 첫 실행도 종료 1로 남깁니다. 파일 manifest의 symlink
별칭을 실제 대상 이름으로 바꿔 조회하는 오류였습니다. 실제 대상 바이트
해시는 계속 검사하면서 manifest 키는 원래 별칭을 사용하도록 새 판독기
사본을 수정했습니다. 같은 저장 캡처의 두 번째 판독은 종료 0,
4.135초였습니다. 제품이나 원본 코드를 다시 실행하지 않았습니다.

별도 판독자는 요청/원시 값·원본 송신·DR 대체·단계별 복구와 위 입력
해시를 독립 대조했습니다. 원래 판독기의 결과도 저장 결과와 같았습니다.
client/server는 종료 0이며 AAP service·monitor·daemon은 실행기가
정리했습니다. 소유 프로세스·소켓·SysV IPC·별칭이 남지 않았고 기존
zombie 집합은 변하지 않았습니다. 새 증거 경로 89개의 소유권을 복원하며
