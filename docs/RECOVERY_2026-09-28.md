# One guarded boot — implementation and boundaries

This change replaces persistent experimental preload with an explicit, one-use
trial. It is intended for the pinned NA 74.00.324A firmware. It has host fixture
coverage; this document does not claim that the guard or injected library has
run on a CMU.

## Startup contract

Installation leaves both `/jci/sm/sm.conf` and `/jci/sm/sm_WCP.conf` free of this
package's `libmx5dr.so` token. Existing touch preload tokens, order, WCP arguments
and unrelated changes are preserved. Two narrowly marked additions to
`/usr/bin/autostart` run the standalone guard immediately before the existing
normal or WCP Service Manager launch. The branch already selected by OEM startup
chooses the baseline path. No service plugin path becomes a shell script.

The guard resides at `/data_persist/mx5-aa-dr/guard/mx5dr-guard`; its directory and
arm manifest are root-owned and outside cmu-writable logs. The guard does not link
or load the experimental DSO. The USB compatibility correction supports the
stock `/data_persist -> /mnt/data_persist`, `/mnt -> /tmp/mnt` aliases. UID 0,
non-writable-by-others and no-symlink checks apply to our installation subtree.
The stock SM files are regular-file checked and bound by their hashes; their
stock 0775 modes and parent directories are not changed. The manifest covers
the libraries, owned configuration, both baselines and both trial templates.
Later touch/config changes invalidate an existing arm rather than restore a
stale saved config.

Each template also records the SHA-256 of its source snapshot. `check`, `arm`
and `select` compare that identity with the current baseline, so a touch edit
between template generation and arming cannot bind a new baseline to an old
template. Explicit `arm.sh` regenerates both pairs while disarmed.

`mx5dr-guard check` validates these inputs and the boot ID without arming. The
installer runs it before publishing its autostart edits. New verification is
recorded in [USB_INSTALL_2026-09-29.md](../validation/USB_INSTALL_2026-09-29.md);
the original test counts below are historical.

Only a valid arm permits an exclusive `/tmp/mx5dr-trial-XXXXXX/sm.conf`. Before
printing this path the guard writes/fsyncs the trial, renames `arm` to `consumed`,
fsyncs the guard directory, and writes/fsyncs a boot-ID marker. Any failed checked
operation returns nonzero without a trial path. Autostart accepts only the fixed
temporary path shape and otherwise retains its original baseline variable. A
missing or non-executable helper also leaves baseline selected. A successfully
selected trial requests the separate collector before the original SM launch;
that request is not evidence of collector readiness.

**Guarantee within this contract:** once consumption has succeeded, later
invocations and the next boot use baseline unless an explicit new arm is created.
An arm is also prevented from selecting twice in the same boot. No automatic
rearm occurs. Root explicitly runs `sh /data_persist/mx5-aa-dr/tools/arm.sh` for
another OBSERVE boot; `--mode=SCRUB` or `--mode=SHADOW` are deliberate alternatives.
ASSIST remains rejected. Installation defaults to one OBSERVE boot; `--mode=OFF`
stages no arm. No script issues a service kill, restart or reboot.

## Interrupted installation and removal

Installation removes any old arm and syncs first. All edits are prepared before
publishing, both persistent configs are cleaned, and autostart is published before
the final arm command. An interruption before arm creation cannot authorize a
new trial. If arm publication fsync fails, the helper removes the arm and checks
directory fsync again. Failure to confirm that cancellation is reported explicitly;
no baseline durability promise is made when the filesystem refuses it. New installations start with clean baseline configs. An older permanent
installation is rejected before payload or startup changes: run its removal
operation first, then install this package. There is no automatic migration
window in which the new DSO could load through an old permanent token. File renames are atomic individually, not as one
cross-file transaction. `pending` refuses blind retry after an incomplete commit;
removal disarms and removes only this package's current tokens/owned startup
blocks. A stale install lock requires inspection through existing access.

Uninstall stages OFF, removes owned autostart blocks and any old permanent token,
and preserves current touch/unrelated edits. It retains library, tools and logs
because running processes may already have code mapped. It does not unload code
or replace current files with an old whole-file backup.
Staged replacement contents are synced before rename; unchanged OEM files retain
their existing inode. A stock BusyBox `flock` on `/tmp/.mx5dr-mount.lock` covers
mount inspection through final read-only restoration, even after the persistent
installation lock is removed. The lock file stays in place; the descriptor lock
is released automatically when the installer exits.

## Limits

A running Service Manager may retain and retry the temporary config. This design
does not claim to repair those same-SM retries, nor does it infer semantics from
`retry_count=0`. The next guarded launch is the boundary. It is not a universal
watchdog or a guarantee against a hanging guard, filesystem failure, torn media,
OEM startup changes, unrelated boot failures or loss of recovery access. Checked
fsync is a software durability request, not a promise about failing storage.
A failure before arm consumption can leave authorization for a later attempt,
but no trial path was published at that point. No OEM binary is modified.

## Verification performed

`python3 tests/recovery/test_guard.py` passes 14 host tests, including:

- no arm; bound-hash drift; root file modes/symlinks; WCP preservation;
- eight concurrent selectors (one successful selection);
- injected failure at trial-directory, post-consumption-directory and boot-marker
  directory fsync, with no published path; failed arm-publication fsync revokes
  the already-renamed arm and a subsequent selector declines;
- an authored host preload DSO aborting in its constructor and a separate authored
  executable aborting after entering main; after prior consumption a new boot-ID
  selects baseline in both cases (no OEM launcher or ARM code executed);
- normal/WCP shell branch execution, exactly one selected helper call, missing,
  nonzero and malformed-output fallback;
- paired editor blocks, duplicate/wrong anchors, CRLF refusal, idempotence and
  preservation of later unrelated edits.

Packaging tests read supplied private firmware fixtures as data only:
`MX5DR_STOCK_ROOT=/path/to/private/rootfs python3 -m unittest discover -s tests/packaging -v`.
Eleven tests pass, including actual stock autostart install/uninstall byte roundtrip,
clean persistent configs, multiline touch coexistence and pending recovery. One
optional release-payload test skips when no bundle has been built. These fixtures
use synthetic non-runnable ELF headers; they do not establish target ABI behavior.

Production compilation must omit `MX5DR_GUARD_TESTING`. That macro alone enables
host fixture-root and fault-injection environment variables; they are not present
in the production build. Build the helper from `src/guard/guard.cpp` and
`src/runtime/sha256.cpp` using the same target softfp toolchain. `make_bundle.sh`
expects the built helper beside `libmx5dr.so`, packages its hash, and never runs it
on the host. The installer also validates its ARM32 little-endian ELF envelope.

Integration follow-up: production guard was built with pinned GCC 4.9.1. The 14-test harness also passed with its guard executable running under ARM/QEMU; shell/editor and crashing helper fixtures remain host code. All 13 combined packaging tests passed with the built library fixture present. See `validation/INTEGRATION_2026-09-28.md` for exact scope.

## 2026-10-06: persistent BETA policy (v1.0)

The text above is the historical one-boot design and stays valid for OBSERVE/SCRUB/SHADOW trials
and for BETA installed with `--one-boot`. By owner decision v1.0 BETA is an always-on product, so a
BETA install now enables a *persistent* policy instead of arming one boot
([design](../validation/PERSISTENT_GUARD_DESIGN_2026-10-06.md),
[verification](../validation/PERSISTENT_GUARD_2026-10-06.md)).

Unchanged: both SM configs stay free of our preload, the owned autostart block runs the guard before
each SM launch, only a printed `/tmp/mx5dr-trial-XXXXXX/sm.conf` replaces the baseline, and any
guard failure leaves the stock baseline. Changed: `mx5dr-guard enable` writes a root-owned
`persist` manifest bound to the same eight input hashes as `arm`, plus `persist-state`. On every new
Linux boot `select` judges the previous product boot from a clock-free fingerprint of the SM reset
reports (`/data/*.out`), trips to stock after two consecutive failed boots (or a runtime
`disable-next-start`), and otherwise publishes the trial after the attempt record and `last-boot`
are durable. The enabling boot and a second selection in one boot never select. A trip stays until
menu 1 re-enables; menu 4 removes `persist` and the autostart blocks as before. The boot-loop rule
based on the runtime `healthy` marker is implemented but compiled off until the runtime writes it.
None of this ran on a CMU.

### 2026-10-06 G2 revision: confirmation, caps and hang bound

After two reviews: a product boot that fails without an SM reset report is now bounded. The owned
autostart block backgrounds `mx5dr-guard confirm` 90 s after a selection; it confirms the boot only
while the SM runs with that boot's trial. The first boot after menu 1 must be confirmed (probation);
later, 3 consecutive unconfirmed boots, 2 consecutive reset boots or 3 reset boots within 10 trip to
stock. The select call is wrapped in the stock BusyBox `timeout -t 15 -s KILL` and the guard bounds
itself with `alarm(10)`. Declines are recorded in `guard/last-decision`; `mx5dr-guard verify` and
`status` (read-only) feed menu 2. Details and the remaining unbounded cases:
[design, revision G2](../validation/PERSISTENT_GUARD_DESIGN_2026-10-06.md#revision-g2-2026-10-06-after-two-independent-reviews).
