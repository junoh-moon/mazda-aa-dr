# 0.1 후속 리뷰와 해결 조건

아래는 **0.1 미수정 기준선에서 제기한 리뷰 기록**이다. 이후 R1/R2와 다음 기동 경계의 R3를 구현했다. 현재 상태·검증·남은 범위는 [STATUS_KO.md](STATUS_KO.md)와 [통합 검증](../validation/INTEGRATION_2026-09-28.md)이 우선한다. 리뷰 의견을 그대로 확정 사실로 승격하지 않고 코드에서 확인한 결함, 이미 처리된 부분, 새 실험 가설을 구분한다.

## R1 — OFF와 disable이 순정 로딩 의미를 보존하지 못함

심각도: 설치 차단. `src/runtime/runtime.cpp`의 dlopen interposer는 609–614행에서 RTLD_NOW 조회/로드를 수행한 다음 bootstrap의 532–536행에서 설정과 disable 표식을 검사한다. NOW 로드 실패 시 원 flags 재시도도 없다. 줄 번호는 0.1 기준이며 이후에는 함수와 diff를 따른다.

수정 방향:

- 설정·OFF·disable 판정을 자신의 추가 대상 dlopen/probe보다 먼저 한다.
- OFF 또는 무효 설정이면 원래 path/flags와 로딩 결과 계약을 보존한다.
- 활성 모드의 NOW 로드가 NULL이면 원 flags로 한 번만 재시도하고 그 로드에는 후크를 설치하지 않는다. 원인과 fallback 결과를 기록한다.
- 재진입·동시 최초 호출·이미 로드된 대상·NOLOAD·비대상·NULL path를 구분한다. errno와 dlerror, boot_attempted 상태를 명시적으로 검토한다.

검증: LAZY는 로드되지만 NOW는 실패하는 미해결 심볼 합성 DSO, 두 방식 모두 실패하는 DSO, 정상 DSO로 실제 interposer를 시험한다. OFF·무효 설정·disable에서 부가 NOW 로딩이 없음을 확인한다. 실제 BLM의 strong undefined symbol은 정확한 의존성·버전·scope·preload 순서를 포함해 별도 점검한다.

한계: NULL 반환 fallback은 생성자 내부 signal/abort/hang을 복구하지 않는다. NOLOAD|NOW가 기존 LAZY 객체를 반드시 승격한다는 주장은 확정 결함으로 기재하지 않는다.

## R2 — D-Bus/SMDB 폴링을 OEM AA 프로세스 밖으로 이동

심각도: 설치 전 수정. worker는 D-Bus를 뒤늦게 초기화하고, 관찰용 SMDB 세 필드를 자식 프로세스로 반복 조회한다. 같은 worker에서 동기 D-Bus 호출도 하므로 ring 배출과 health 기록을 지연시킨다. 현재는 후크 설치 실패 후에도 worker가 시작될 수 있다.

수정 방향: 별도 collector 프로세스가 자기 프로세스 초기화 단계에서 D-Bus 스레드 초기화를 마치고 SMDB/D-Bus를 읽는다. AA 프로세스에는 후크·ring·writer만 남긴다. AA worker 안에서 collector를 매 주기 생성하는 구조로 바꾸어서는 안 된다. 수집기 시작·중지·권한·로그 상관관계는 별도 계약으로 둔다.

검증: preload의 D-Bus 의존성과 폴링/자식 생성이 제거됐는지 확인한다. collector crash/hang/버스 단절이 OEM 송신 및 ring writer에 영향을 주지 않는지 시험한다. 수집 시각은 `observed_at`이며 생산 시각은 unknown으로 보존한다. 현재 코드의 SIGKILL 후 blocking waitpid 때문에 전체 raw_field 호출이 엄격히 250ms 이내라는 주장도 하지 않는다.

버전 주의: DBus 1.6.30/glibc 2.11은 빌드 sysroot에서 확인한 버전이다. 이것만으로 실차 runtime 버전을 확정하지 않는다. 구버전 DBus 초기화 조건은 [공식 문서](https://dbus.freedesktop.org/doc/api/html/group__DBusThreads.html), 당시 spawn 경로는 [glibc 유지관리자 설명](https://sourceware.org/pipermail/libc-help/2010-October/001585.html)을 참고한다.

## R3 — 일반 크래시·preload 로더 실패의 재부팅 반복 복구

심각도: 설치 차단. 현재 `disable-next-start`는 RX 복원 실패 경로에서만 작성한다. write/fsync 오류도 확인하지 않는다. 일반 SIGSEGV/ABI 오류, 동작 중 지연 크래시, 라이브러리 매핑/재배치 실패는 이 경로로 보호되지 않는다. jciAAPA 서비스의 reset_board 설정 때문에 전체 CMU 재시작으로 이어질 수 있다.

`starting`을 후크 설치 전 fsync하고 정상 동작 뒤 지우는 센티널은 일부 시작 실패를 감지하는 후보지만 완전한 복구 장치는 아니다. AA 연결이나 첫 LOCATION 이전에 타이머가 끝나면 해당 경로는 보호하지 못한다. 자체 코드 실행 전 발생하는 preload 실패도 내부 센티널로 막을 수 없다.

필요한 설계: 실제 CMU 서비스 시작 경로에서 이 라이브러리가 매핑되기 **전**에 preload 포함 여부를 결정하는 외부 보호 위치를 확인한다. LD_PRELOAD가 이미 적용된 shell wrapper는 보호 장치 자체가 먼저 실패할 수 있어 해결책이라고 단정하지 않는다. 서비스의 plugin형 lifecycle과 IPC를 보존해야 한다.

검증 조건: 초기 후크 크래시, 첫 AA 사용 시 크래시, 보호 시간 이후 지연 크래시, preload 의존성/재배치 실패, 표식 저장 실패와 전원 단절에 대한 동작을 명시한다. 어떤 실패까지 자동 복구하는지 범위를 선언하고 다음 시작에 정상 경로로 복귀하는 증거를 확보한다. 타이머 몇 분만으로 전체 세션 복구를 보장했다고 하지 않는다.

현재 판단: 필요성 확정, 삽입 위치·구현·실차 검증 미완료. root 셸 접속 가능성만으로 해결 처리하지 않는다.

## R4 — SCRUB과 DROP은 검증할 가설

SCRUB은 speed/bearing의 **유무 flag를 false**로 만든다. 유효한 속도 0을 보내는 것과 다르다. 그러나 오래된 좌표를 계속 보내므로 폰의 위치 융합을 방해하거나 터널 진행을 악화시킬 가능성은 남는다. Android [Location API](https://developer.android.com/reference/android/location/Location)의 optional field 의미와 특정 AA fallback 정책을 혼동하지 않는다.

DROP은 mode=0 캐시 LOCATION을 생략하는 비교 후보다. 폰 GPS/추정으로 반드시 넘어간다는 증거는 아직 없다. 현 adapter의 exactly-once 원본 send 불변식과 다른 동작이므로 caller가 반환값을 어떻게 쓰는지, send가 갖는 상태·소유권·오류 부작용을 먼저 분석해야 한다. OBSERVE 반환값 분포만으로 가짜 성공 반환값을 정하지 않는다.

구현 시 계약: 선택된 DROP LOCATION은 원본 send 0회, 나머지는 1회. 반환값/errno와 부작용을 별도로 정의하고 테스트한다. 기존 exactly-once 검사를 조용히 약화시키지 않는다.

실험 판정: 설정 이름이 아니라 실제 SCRUBBED/DROP 이벤트와 시간 구간을 사용한다. `audit_fault`, drop, 로그 누락, 폰/앱 버전·연결 방식·native provider 상태를 함께 기록한다. 차량 send 성공은 폰 수용 증거가 아니다. 조작과 회수는 주차 중에만 한다.

## R5 — 이미 처리된 항목과 낮은 우선순위

- `tools/analyze_logs.py`는 이미 audit_fault/drop을 불완전 관측으로 판정한다. 신규 구현 사항으로 중복 기재하지 않는다. 실제 SCRUB 변형 구간 분석은 개선 여지가 있다.
- `sm.conf.mx5dr-new.*` 잔여 파일 정리는 해당 설치 transaction 소유 범위만 대상으로 한다. 다른 설정 파일을 wildcard로 지우지 않는다.
- 로그 용량 8MiB×3 제한은 총 flash 기록량 제한이 아니다. 시간당 10–20MB는 측정값이 아니며, 실험 데이터로 확인해야 한다.
- veneer, LOCATION 오프셋, 합성 ABI 시험, ASSIST 차단의 긍정 검토는 유지한다. 이것들이 R1–R3를 해결해 주지는 않는다.
