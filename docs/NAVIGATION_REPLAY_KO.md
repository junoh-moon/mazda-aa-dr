# 원본 로그의 항법 재생과 보정 비교

차량에서 한 번 수집한 SHADOW 원본 로그로 같은 센서 입력을 반복 계산한다. PC 프로그램이 실제 `Pipeline`, `GpsHoldout`, 공통 DR 코어를 호출한다. 수학을 Python으로 다시 구현하지 않는다. 코드 수정이나 보정 비교 때마다 같은 경로를 다시 운전하는 일을 줄이는 용도다.

이 변경은 PC 도구다. 차량 설치 기본값·AA 송신·ASSIST 차단을 바꾸지 않는다. 기존 #10의 SCRUB/DROP 바이트 정책 재생과도 별개다.

## 사용

C++11 빌드 환경과 Python 3가 있는 Linux PC에서 저장소를 받고 실행한다. ARM 도구체인이나 CMU 연결은 필요 없다.

```sh
make replay-navigation
python3 tools/replay_navigation.py exported-logs.tar.gz --json
```

기존 `python3 tools/analyze_logs.py exported-logs.tar.gz`는 코드 재생 없이 기록 자체를 점검한다. 새 센서 요약도 이 명령에 포함된다. 두 명령 모두 PC에서 실행한다.

## 어떤 기록을 계산하는가

원본 `motion`/`motion_batch`의 wheel·yaw·reverse와 AA 후크의 `position`을 사용한다. collector의 SMDB 폴링을 센서 입력으로 대체하지 않는다. 압축 파일은 추출하지 않고 기존 분석기의 경로·크기·JSON 검사를 재사용한다. 좌표·원본 payload를 요약 보고서에 넣지 않는다.

한 번의 SHADOW 세션을 입력으로 받는다. 누락된 boot/health, 수신 순번 누락·역행, 소스 재시작, audit fault, 잘못된 형식 등 입력 근거가 불완전하면 계산을 보류한다. 마지막 health가 마지막 POSITION·센서 수신 이후까지 포함해야 한다. OBSERVE 기록에는 이 항법 재생에 필요한 원본 VBS 센서가 없으므로 SHADOW 원본 로그가 필요하다. 입력은 최대 500,000개 JSON 행·250,000개 재생 이벤트로 제한한다.

기존 로그에 정상적인 GPS 단절에 따른 holdout ABORT가 있거나 마지막 비교 구간이 아직 끝나지 않았다는 사실과, 원본 입력 자체의 손상을 구분한다. 재생에 쓰지 않는 collector의 시작/종료 누락도 원본 센서 손상과 구분한다. 기존 기록의 경고를 지우지 않으며 새 재생의 비교 통계도 완료된 구간에만 한정한다.

## 재생 규칙과 한계

로그에는 각 콜백의 수신 시각은 있지만 AA worker가 큐에서 꺼낸 정확한 시각과 모든 drain 시점은 없다. 따라서 이 도구는 **같은 입력으로 수행하는 명시적인 오프라인 MODEL 재계산**이며, 당시 CMU 실행 순서를 완전히 복원했다고 주장하지 않는다.

관측 수신 시각으로 정렬하고 같은 시각은 POSITION 뒤 motion 수신 순번으로 처리한다. 같은 시각의 입력을 모두 넣은 후 공통 100ms 정렬 대기를 적용한다. 마지막 입력 이후의 미래 센서를 만들거나 시간을 늘려 비교 구간을 억지로 완료하지 않는다. 끝의 대기 구간과 진행 중 비교는 결과에서 빠질 수 있다.

원본의 source timestamp와 raw/count/reverse 필드를 유지하며, receipt time을 생산자 측정 시각으로 승격하지 않는다. 이 재계산과 당시 SHADOW 로그가 다르다면 큐 지연·누락·worker 처리 시점도 조사해야 한다.

## 보정 전후 비교

동일한 입력을 두 설정에 넣는다.

| 설정 | GPS 검사 | 자이로 영점·휠 거리 |
| --- | --- | --- |
| fixed | 현재와 같은 기준점 검사 | 연구 프로파일의 고정 영점·scale 1 |
| adaptive | 현재와 같은 기준점 검사 | 현재 자동 보정 코드 사용 |

fixed의 GPS 검사를 느슨하게 하여 비교하지 않는다. 학습 여부만 별도로 선택하는 내부 API를 추가하며 차량 worker의 기존 기본값은 유지한다. 각 계산은 자체 위치 상태와 보정 근거를 가지며, holdout 동안 참조 GPS는 계산이나 학습에 들어가지 않는다.

비교 통계는 **기준점 시각과 참조 시각이 같고 양쪽 모두 정상 종료한 구간**에서만 계산한다. 한쪽만 시작/종료한 구간, ABORT, 잘린 구간과 짝이 없는 참조 수를 함께 남긴다. 시작 전 ABORT 횟수는 실제 시작한 구간 수와 분리한다. 서로 다른 구간의 평균을 나란히 놓고 보정 효과라고 해석하지 않는다.

위치 차이(m), 부호 있는 방향 차이(rad), 방향 차이의 절댓값(rad)을 각각 요약한다. 부호 있는 평균은 양·음 오차가 상쇄될 수 있으므로 방향 오차 크기를 대신하지 않는다. 각 통계에는 fixed/adaptive와 동일 참조에서의 `adaptive_minus_fixed`를 남긴다. 사용한 재생 실행 파일의 SHA-256도 보고서에 기록한다.

숫자는 GPS 대비 차이다. matched 구간은 전체 주행의 일부일 수 있고 GPS도 참값이 아니다. 자동 합격, 보정 우승 판정, 실제 위치 정확도나 네이버 지도 수용을 추론하지 않는다. 주 항법 파이프라인의 실제 mode=0 계산 상태도 요약하지만, 이를 AA에 송신하지 않는다.

종료 코드 0(`comparison_produced`)은 비교 숫자를 만들었다는 뜻이다. 1은 로그 계약 위반, 2는 비교 불충분/입력 또는 실행 오류다. 0도 실차 합격을 뜻하지 않는다.

## 첫 센서 기록 요약

기존 분석기에 센서별 관측 유무·표본 수·수신 간격·최대 간격과 250ms 초과 간격 수를 추가한다. 세션/소스 epoch 경계를 넘어 시간 간격을 연결하지 않는다. 이 250ms는 현재 MODEL의 제한과 비교하기 위한 진단 기준이며 차량 센서의 명세나 새 합격 기준이 아니다.

원본 수신 시각만으로 생산 지연이나 물리 측정 주기를 확정하지 않는다. 이미 기록하는 GPS 기준점 거부 사유와 휠 보정 요약도 함께 확인할 수 있다. 새 프로세스·운전 중 명령·설정 파일은 추가하지 않는다.

검증 결과와 실제 실행 제한은 [검증 기록](../validation/NAVIGATION_REPLAY_2026-09-29.md)에 따로 적는다.
